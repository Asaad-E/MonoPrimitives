# Decisions — the *why*, condensed

Why things are the way they are, grouped by area so you can jump to what you're touching instead of scanning a chronological log. Check here before "fixing" something that looks wrong — it might be deliberate. Git history has the full session-by-session narrative if you ever need it; this file only keeps the reasoning that still matters for working in this codebase today.

## Packaging & scope

- **One assembly, not a multi-package split.** `MonoPrimitives.dll`, raylib/MonoGame.Extended-style. `Core/`/`2D/`/`3D/` stay separate source folders; only the number of installable NuGet artifacts changed.
- **Namespaces unified under one root** (`MonoPrimitives`, `MonoPrimitives.Primitives2D`, `MonoPrimitives.Primitives3D`). They used to be unrelated bare namespaces (`Primitives2D`, `MonoPrimitives3D`) with no naming signal they were one package.
- **Core-sharing rule: code identical apart from namespace goes in `Core/`; genuinely different 2D/3D code stays duplicated.** Forcing different math into one shared abstraction just to avoid duplication isn't worth it. `SpatialHashGrid2D`/`3D` were removed entirely rather than moved to Core — out of scope either way.
- **No physics resolution, ever.** `Collision2D`/`Collision3D` detect overlaps only. A Verlet-based resolution module was built once and deleted for crossing this line.
- **`GridRenderer2D` (texture-backed grid/heatmap renderer) removed — out of scope.** Measured ~1000x faster than per-cell `FillRectangle`, but it's a ready-made *system* (owns a texture, its own lifecycle), not a building block. Same reasoning kept a particle system and a cellular-automata helper out.
- **`Plot2D` was removed.** A dedicated charting library will always render better axes/legends than a bolt-on chart type. This library draws shapes; plotting real data belongs elsewhere.
- **Retargeted from `net10.0` to `net8.0`.** `net10.0` was never a deliberate choice, just whatever was newest when the project started — most MonoGame consumers are on `net8.0` (current LTS), and a library on a newer TFM can't be referenced by an older-TFM project.
- **Every `examples/` project needs its own `app.manifest`.** Without one declaring DPI awareness, Windows renders the window at logical size and bitmap-stretches it on any scaled display — blurring everything, including `DebugFont5x7`'s pixel-art glyphs, regardless of what the app draws. All 13 examples were missing this at first (only the sample had it); reported as "every test looks blurry."
- **`ObjectPool<T>`, `RingBuffer<T>`, `Cooldown`, and `Vector3Extensions` were added — a different kind of addition than the "no prebuilt systems" rule above rules out, and worth naming why.** The filter: does this save you from writing something you were going to write anyway (a utility), or does it ask you to organize your game around it (a system)? `RectangleF`/`FrameLimiter`/`FpsCounter`/`Camera2D` already pass that test — none of them know anything about your game, they just stop being useful the moment you stop calling them. `ObjectPool<T>`/`RingBuffer<T>`/`Cooldown` are the same shape: `RingBuffer<T>` is literally the same ring-buffer logic `Trail2D`/`Trail3D`/`FpsCounter` already each hand-roll privately, generalized; `ObjectPool<T>` doesn't know what `T` is or does, no update loop, no ownership; `Cooldown` is a struct precisely so it can be a field on hundreds of simulation entities without becoming its own heap-allocated "thing" to manage. `Vector3Extensions` is the more mundane case — a real, verified gap (confirmed by reflecting on the actual MonoGame assembly, not assumed) matching `Vector2Extensions`'s existing shape. A companion `MathUtil` class (`Remap`/`Wrap`/`LerpAngle`/`DeltaAngle` — also confirmed genuinely missing from `MonoGame.MathHelper`, which can't be extended since it's a `static class` and extension methods need an instance receiver) was considered and deliberately left out: three simple functions didn't justify a whole new class, and anyone who needs them specifically will write them in five minutes anyway. `PrimitiveInput` gaining `Current`/`PreviousKeyboardState`/`MouseState`/`GamePadState` accessors is the same instinct applied to an existing class: `RandomUtil.UnderlyingRandom` already sets the precedent — don't force a caller who needs one specific thing this class doesn't wrap to poll a second, desynced snapshot themselves. A follow-up pass audited the rest of `src/` for the same pattern (a `private readonly` field wrapping something constructed internally, genuinely unreachable otherwise) rather than guessing: `Primitive2DBatch`/`Primitive3DBatch`'s own `BasicEffect` (constructed in the constructor, previously reachable only by fully replacing it via `Begin`'s `effect` parameter, not tweaking one property on the existing one) and `FrameLimiter`'s `Stopwatch` (no way to read elapsed time mid-frame without waiting for `EndFrame()`) both qualified — added as `Effect`/`Elapsed`, both read-only specifically so nothing outside the class can call a mutating method (`Stop()`/`Reset()` on the stopwatch) and break the class's own invariants. Fields that *were* checked and rejected: every class's own `GraphicsDevice` field (the caller already passed that exact instance in, so echoing it back adds nothing), `Camera2D`/`Camera3D`'s three internal `Noise` instances backing screen shake (not independently useful — `GetShakeOffset()` already exposes the meaningful output), and every batch's raw vertex/index arrays and `Trail2D`/`Trail3D`/`FpsCounter`/`RingBuffer<T>`'s own backing arrays (exposing those would let a caller violate the ring-buffer/batch invariants the class exists to protect — already safely reachable through each class's own indexer/computed properties instead).
- **`DebugTimer` (a user-supplied `IDisposable` stopwatch-and-print struct, ported roughly as-is) took `label` as a required constructor argument, not `[CallerMemberName] string label = ""`.** The auto-label idea was tried first and reverted after a real repro: for a **struct**, `new DebugTimer()` (empty parens, no arguments at all) does **not** call a user-defined constructor whose parameters are merely optional — the language spec special-cases the zero-argument `new S()` form to always mean "the all-fields-default value of `S`", bypassing any constructor unless it's a truly zero-parameter one (which can't carry `[CallerMemberName]`, since there'd be no parameter to attribute). Confirmed with an isolated repro (`new S()` on a struct with `S(string label = "default")` prints `null`, while `new S("x")`/`new S(label: "x")` both work correctly) before reverting — this would have silently produced a `default`-valued, non-functional timer (null label, a zero timestamp read back as a multi-hour "elapsed" time) for exactly the empty-parens call style the feature was meant to make convenient, with no compiler error to catch it. A caught-by-a-real-test example, not just reasoning: the first test run printed `[] 16359668.60 ms` instead of the expected `[Run]`.
- **`Vector3Extensions` gained `AngleTo`/`AngleToSigned(other, axis)`/`Rotated(axis, radians)` in a follow-up pass — deliberately left out the first time since they weren't named when the class was originally proposed, added once actually asked for.** Confirmed genuinely missing from `Vector3` the same way as the rest of the class (reflection against the real assembly, not assumed). Unlike 2D's `AngleToSigned(other)`, the 3D version needs an explicit `axis` parameter — a signed rotation only means something once you've picked which axis you're turning around (`+PI/2` around `+Y` sends `+X` to `-Z`; around `-Y` it would send `+X` to `+Z` instead, a genuinely different result, not a sign-flip quirk) — verified directly (`Quaternion.CreateFromAxisAngle` + `Transform` on a concrete case) rather than assumed before writing the doc comment's claim. **The cross-check test between `AngleToSigned` and `Rotated` first failed on a real-looking mismatch that turned out to be the test comparing the wrong vectors, not a bug in either method** — worth recording since it's exactly the kind of thing "reasoning alone" gets wrong: the test rotated a random vector `a` (which generally has some component *along* the rotation axis) and compared the result to `b`'s direction — but axis-angle rotation leaves a vector's own axial component untouched, so renormalizing the rotated `a` mixes that untouched component back in, and the result doesn't line up with `b`'s direction unless `a` happened to already be perpendicular to the axis. Confirmed by hand-tracing one failing case with real numbers: rotating `a`'s own *flattened* (perpendicular-to-axis) direction by the computed angle landed on `b`'s flattened direction exactly (dot product `1.0`); rotating unflattened `a` gave `0.58`. Fixed the test to flatten before rotating, matching what the two methods' contract actually promises about the rotation plane, not the whole vector.
- **`Vector2Extensions.Slide`/`Vector3Extensions.Slide` were added alongside `Reflect` (already native on both types), not as a replacement for it.** `Reflect` bounces — it flips the normal component of a vector. `Slide` — the standard "keep moving along the wall/floor/slope you just hit" character-movement move — instead drops the normal component entirely, keeping only the tangential part (`v - normal * Dot(v, normal)`). Genuinely different operations with genuinely different uses (a bouncing projectile vs. a walking character), confirmed neither exists natively on `Vector2`/`Vector3` before adding. `normal` must already be unit length, matching `Reflect`'s own existing convention — not re-normalized internally.

## API conventions

- **No `Ex`/`V`-suffixed method siblings — a parameter variant is an overload of the same name.** `FillSphereEx`/`FillCylinderEx`/`FillCubeV`/`DrawArrow3D`/`DrawFrustumWires` all got folded into the plain `Fill*`/`Border*`/`Draw*` name as a new overload, matching CODESTYLE.md's own rule.
- **`Draw<Shape>`'s single-color and `fillColor, borderColor` overloads merged into one signature per shape**, in both 2D and 3D: `Draw<Shape>(..., Color fillColor, Color? borderColor = null, ...)`. Apos.Shapes (this project's own naming source) does the same — one overload, no color-count split. Cut every 2D `Draw*` pair roughly in half, and in 3D closed a real gap: every 3D `Draw<Shape>` used to require both colors, so `DrawCube(pos, size, Color.Green)` didn't compile. Position/size overloads (`Rectangle` vs `Vector2` vs raw floats) stayed separate — those are real type differences, not a color default in disguise.
- **3D line-stroke methods take `thickness`, not `width`.** Every other `Border*`/`Draw*` method already used `thickness`; only the line family had drifted. `FillCube`/`BorderCube`/`DrawCube`'s `width` is untouched — that's a real box dimension, a different concept.
- **2D's two `DrawArrow` overloads collapsed into one**, `color` before `thickness` (C# requires required params before optional ones, so the simple overload already had no choice).
- **`Camera3D.GetScreenToWorld`/`GetWorldToScreen` renamed to `ScreenToWorld`/`WorldToScreen`**, dropping `Get` to match `Camera2D`. `GetScreenToWorldRay` kept its prefix — "get a ray" reads as fetching a distinct object, unlike a plain conversion.
- **Rectangle's `*RoundedGradient`/`*ChamferGradient` renamed to `*GradientRounded`/`*GradientChamfer`** to match Triangle/Poly/Polygon's existing "Gradient first" order; `GetSplinePointBezierQuad` renamed to `GetSplinePointBezierQuadratic` to match `DrawSplineBezierQuadratic`. Both breaking, done deliberately while pre-1.0 — the cheapest point to fix a naming mistake.
- **2D's ray checks return `bool` + `out` params; 3D's return a `RayCollision3D` struct.** Not unified on purpose: a 3D raycast often needs to compare `Distance`/`Normal` across several candidate hits before deciding which is "the" hit, so a reusable struct pays for itself; 2D's checks are almost always an immediate yes/no gate where the extra allocation-free `out` params are the lighter fit. Naming follows the split — `Check*` for 2D's yes/no, `Get*` for 3D's result struct.
- **Triangle's `(center, radius, rotation)` overload is a one-line wrapper over `FillPoly(sides: 3)`**, not separate vertex math — a triangle already is a regular 3-sided polygon, so it inherits the same rotation convention for free.
- **Never name "raylib" or other design inspirations in doc comments or `Guide/*.md`.** Internal implementation comments may reference an algorithm's origin; the root `README.md`'s own "Inspiration" section is the one deliberate exception. See CODESTYLE.md.

## Camera & viewport

- **`Camera3D` merges camera + controller into one class**, unlike raylib's split — a better fit for C#'s OO style. `Camera2D` mirrors the same shape; it used to have no input handling at all, so every caller (including the sample) hand-rolled WASD-pan/wheel-zoom/drag-pan from scratch.
- **`Camera2D`/`Camera3D` both take their `ViewportAdapter2D` at construction, not per call.** An earlier pass added `ScreenToWorld(pos, adapter)`-style overloads that worked but forced passing the same adapter at every call site — redone to match MonoGame.Extended's `OrthographicCamera(ViewportAdapter)` shape instead. `Camera2D.Offset` defaults to the adapter's virtual center but stays a plain mutable field, so a caller wanting a different anchor (this project's own 2D gallery sets `Offset = Vector2.Zero`) just reassigns it after construction.
- **Both cameras split into two `Update` tiers**: `Update` (passive — decays shake, settles zoom easing, nothing else) and `UpdateWithInput(PrimitiveInput, ...)` (the built-in WASD/mouse controller). The plain `Update` used to *be* the input-reading one, which meant there was no way to use a camera without silently getting WASD/drag baked in.
- **`CameraInput`/`CameraInput2D` structs were removed** — `UpdateWithInput` reads keyboard/mouse straight from the caller's own `PrimitiveInput` instance instead of an intermediate struct. The struct was solving a decoupling problem (input source vs. camera logic, for replays/tests) this library was never trying to solve; every real caller just wanted "read my input, move the camera." `UpdateWithInput` deliberately never calls `PrimitiveInput.Update` itself — the caller updates it once per frame and hands the same instance to everything.
- **`Camera3D`'s right-drag mouse-look negates just the mouse contribution** (`yaw -= mouseDelta.X * ...`), matching "grab the world and drag it" rather than an FPS "steer where you push" feel — `Camera2D`'s own left-drag pan already uses that convention. Q/E moved from roll to yaw (more commonly reached-for next to WASD); the old roll behavior moved to Z/X.
- **`Camera2D` has no parameterless constructor — use `CreateDefault()`.** Matches `Camera3D`, which never had one either. A bare `new Camera2D()` as a field-initializer placeholder doesn't signal "this is a placeholder" the way a named factory does.
- **`Camera3D.Reset()`/`Camera2D.Reset()` restore construction-time pose and clear follow/zoom/shake state, bound to `R`.** `UpdateWithInput` returns immediately on the reset frame so a same-frame input delta can't fight it. `Camera2D` got `Reset()` later than `Camera3D` did, added with the identical shape once asked for.
- **`Primitive3DBatch.Begin(camera)` calls `camera.ViewportAdapter?.Apply()` internally instead of taking a separate viewport argument.** Without it, a 3D scene sharing a window with letterboxed 2D content would silently project against the full backbuffer and stretch into the bars — `ViewportAdapter2D.BoundingRectangle` is exactly the on-screen sub-rect a 3D projection needs too.
- **`BoxingViewportAdapter2D`/`ScalingViewportAdapter2D` read `PresentationParameters.BackBufferWidth/Height`, not `Device.Viewport.Width/Height`, for `Scale`/`Offset`.** `Apply()` narrows the device viewport; reading `Scale`/`Offset` again afterward off the narrowed size silently produced a wrong `Offset` (measured 30+ px drift via a round-trip test, 0 after). Relatedly: never call `Apply()` before drawing with `camera.GetTransformMatrix() * adapter.GetScaleMatrix()` — the matrix already bakes in `Offset`, so narrowing the viewport too double-applies it on the Y axis. Both `Apply()` (device-viewport narrowing, used by 3D) and `GetScaleMatrix()` (matrix composition, used by 2D) stay as two separate mechanisms deliberately — that's what lets one adapter drive a 2D and a 3D layer sharing a window in the same frame.
- **`GraphicsDevice.Clear()` ignores a narrowed viewport and always clears the whole render target.** A boxed 3D scene that `Clear()`s again after `Apply()` (to give the "inside" a different color than the bars) silently wipes the bars too. The fix uses existing API — draw a rectangle sized to the current viewport instead, since an actual draw call *is* confined to `Viewport`. Documented on `ViewportAdapter2D.Apply()`'s own doc comment.
- **A `ViewportAdapter2D`-constructed `Camera2D`'s `Offset` re-reads the adapter's virtual center live on every access, until assigned directly once — which pins it.** A one-time snapshot at construction went stale after any resize on `Default`/`WindowViewportAdapter2D` (whose virtual size tracks the live window). MonoGame.Extended's own `OrthographicCamera.Origin` doesn't solve this either (confirmed by decompiling it) — it targets a different mechanism (a `ClientSizeChanged` event) for a different adapter. `Reset()` un-pins `Offset` again.
- **`Camera2D.UpdateWithInput`'s left-mouse-drag pan compensates for `Rotation` before applying the delta.** It didn't used to — breaking the method's own "drag tracks the cursor 1:1" contract whenever the camera is rotated, verified numerically (a 90°-rotated, 2x-zoomed camera's 30px drag used to drift by `(-30,+30)`, now exactly `(0,0)`). Dormant until found, since no sample/demo rotates a 2D camera. `ViewportAdapter2D.BoundingRectangle` was also normalized to round both its offset and size consistently — it used to truncate one and round the other, which could land up to 1px off from the float-precise draw transform.
- **`SmoothZoom`'s "settled" epsilon is `Min(0.0005f, |target| * 0.001f)`, not a fixed `0.0005f`.** `MinZoom`/`MaxZoom` are caller-set; a fixed epsilon is a large fraction of a realistic per-tick delta on a much-smaller-than-default zoom range, so the ease could mark itself "settled" while still measurably short (simulated 27% short on a 0.00001–0.0001 range) and then never get closer, since settling permanently stops it.
- **`Primitive2DBatch.ClearLetterboxed(adapter, barColor?, backgroundColor?)` packages the letterbox-with-a-different-inside-color recipe into one call**: `Reset()` + `Clear(barColor)` + `Apply()` + a `FillRectangle` sized to the narrowed viewport. Must run before the caller's own `Begin()`. A real bug shipped in 0.5.6 and fixed in 0.5.7: it left the viewport `Apply()`'d on return, so the caller's next `Begin(camera.GetTransformMatrix())` double-applied the adapter's offset, rendering the scene off-center — caught from a visibly wrong render, fixed by ending with one more `Reset()`.
- **`BoxingViewportAdapter2D(..., pixelPerfect: true)` floors the fit-scale to a whole number, minimum 1x.** A continuous (fractional) scale draws some source pixels wider than others, which shimmers pixel art specifically. Flooring a uniform scale typically leaves a border on *all 4* sides rather than 2 opposite bars, except when the window size happens to be an exact multiple of the virtual resolution.
- **`FollowTarget` got a box-deadzone overload (`Vector2`/`Vector3 deadZoneHalfSize`) instead of replacing the original.** The existing radial `FollowPadding` deadzone is isotropic (same tolerance every direction); a box is the classic platformer/top-down "camera box" — independent per-axis tolerance (e.g. wide horizontal slack, none vertical). Both share the same smoothing-velocity field, so mixing the two per frame on one camera fights itself — documented, not guarded, matching this library's existing trust-the-caller boundary.
- **`Camera2D.FitBounds`/`Camera3D.FitBounds` set `Zoom`/`Position`/`Fovy` directly, no easing** — a cut, not a pan. In 2D, `Zoom = min(viewportWidth/requiredWidth, viewportHeight/requiredHeight)` (the tighter axis wins). In 3D `Perspective`, the camera moves along its current view direction to `distance = radius / sin(halfFovAngle)` on **both** FOV axes (vertical `Fovy` and the derived horizontal half-FOV via `atan(tan(halfFovy) * aspectRatio)`), taking the max — the standard sphere-fits-in-a-cone distance, verified numerically against `BoundingFrustum.Contains` before shipping (a `Camera3DTests` check builds the fitted frustum and asserts `Contains`, then halves the distance and asserts it's no longer `Contains`). In `Orthographic`, `Fovy` (this library's stand-in for orthographic world-height) grows to fit instead, distance unchanged.
- **`Camera2D.IsVisible`/`Camera3D.IsVisible` are a frustum/rect-culling convenience, not a new visibility system.** 2D reuses `GetVisibleWorldBoundsF().Contains/Intersects`; 3D reuses `GetFrustum(aspectRatio).Intersects(BoundingSphere/BoundingBox)` — both just name an operation callers were already assembling by hand before drawing many objects.

## Collision

- **`Collision3D.GetRayCollisionBox`'s face-normal detection rewritten from a fixed epsilon to nearest-face selection.** The old code compared each of 6 face planes against a hardcoded `1e-3` epsilon, falling back to a hardcoded `+Z` normal if none matched — wrong on ~7% of oblique hits on a 1,000,000-unit box, since floating-point error at that scale routinely exceeds a fixed epsilon even for an unambiguous hit. Picking the minimum distance across all 6 faces is scale-invariant with nothing to tune; verified 0/2000 wrong normals after.
- **2D polygon/mixed-shape checks (`PolyPoly`/`RecPoly`/`RecTriangle`/`TriangleTriangle`) use a shared SAT core; circle/capsule-vs-polygon checks (`CirclePoly`, `CapsulePoly`/`Rec`/`Triangle`) don't.** SAT requires convex input and gives a silently wrong answer on a concave one — verified with a concave "arrow" polygon where SAT would report a false collision. Capsule now has the same `Rec`/`Triangle`/`Poly` coverage every other 2D shape already had, implemented the same way `CirclePoly` generalizes to concave input: true if either endpoint is inside, or the axis segment comes within its radius of any edge.
- **`Collision3D` gained `GetRayCollisionTriangle`/`Quad` (Möller–Trumbore) and `CheckCollisionCapsuleBox`.** The ray checks are raylib parity, confirmed against a live fetch of raylib's own source. `CapsuleBox` completes this library's own Capsule-vs-every-shape matrix (raylib has no capsule collision math at all); segment-to-box distance has no closed form, so it's minimized via ternary search, valid because distance-to-box is convex in the segment's parameter.

## 2D shape rendering

- **Antialiasing is MSAA, a caller-side `GraphicsDeviceManager` setting — not something the library does internally.** A screen-space shader post-process (FXAA-style, then a simpler edge-aware blend) was built and verified rendering correctly, but shelved anyway: it made real content look worse in side-by-side comparison despite passing isolated checks, and MSAA already covers this. A later circle-specific edge-feathering idea hit the same wall for a different reason: a feather ring sized in local space scales with an unknown camera zoom the same way the shape's own facet error does, so it's either invisible or a visible blur depending on zoom — never both a clean edge and a real fix. If a circle is known to be viewed zoomed-in, `FillCircle`'s explicit-segment overload already solves it with no new API.
- **`Fill*Shadow` (drop shadows) are one vertex-colored ring around the shape's own already-generated boundary, not a literal 9-slice.** Built from `OutsetConvexPolygon` (the mirror of `InsetConvexPolygon`) tracing the real boundary outward, opaque at the edge fading to alpha-0 outside — because it traces the real boundary instead of scaling fixed sprites, it automatically supports per-corner radius, rotation, and chamfer with no extra bookkeeping.
- **A `Border*`'s round/bevel `jointRadius` is capped by its own thickness on a sharp corner — a self-intersection guard, not a bug.** An inward-only stroke's fillet can't reach past roughly `thickness × cos(halfAngle)` before crossing the shape's own opposite edge; a 5-point star's ~42° tips will silently clamp a large requested radius down to a few pixels. The clamp is per-corner, not per-edge — two adjacent corners could otherwise together claim over 100% of a shared edge.
- **`FillPolygon` ear-clips instead of always fan-triangulating.** The fan-from-`points[0]` approach needs vertex order to sweep monotonically in angle from that point; a star's alternating outer/inner vertices double back angularly even though the tip can technically "see" the whole shape, producing a torn, overlapping fan. `IsConvex` now gates the two paths: convex or triangle input keeps the original zero-allocation fan, anything else goes through proper ear-clipping. Still requires a simple (non-self-intersecting) polygon.
- **`BorderRing`'s two arcs draw as one joined `DrawLineStrip`, not one `DrawLine` per segment** — independent segments each get their own flat end cap, which don't line up on a curve and read as a sawtooth once `thickness` grows. A partial ring's wedge is one closed outline loop rather than two open strips plus two separate closing lines, for the same reason: primitives that only *touch* at a shared edge don't reliably rasterize with zero gap even when the math agrees exactly.
- **`BuildRoundedOutlineGeometry` must pick which side is "outer" per joint based on that joint's own turn direction, not always the same fixed side.** A joint's `Side` flips with the turn direction (opposite at a zigzag's peak vs. its following valley); treating one side as always-outer produced a self-intersecting (bowtie) quad — a real crack on any open polyline whose turn direction alternates, with `LineJoin.Round`/`Bevel`. Confirmed via a shoelace signed area of exactly 0 (the bowtie signature) before the fix.
- **`InsetConvexPolygon`/`OutsetConvexPolygon`'s reflex-vertex bug fixed — with a simpler rule than first expected.** The old per-vertex "closer/farther from centroid" heuristic only holds at convex vertices. The actual fix needs no per-vertex convex/reflex test at all: for a *closed* polygon, the correct offset candidate at every vertex is the same fixed side of the two miter candidates, decided once from the polygon's overall winding. The open-polyline case (no winding to read) keeps the old centroid-relative logic, since it wasn't the case that was actually broken.
- **Gradient coloring: `FillTriangleGradientRounded` uses exact barycentric weight against the true triangle; `FillPolygonGradient`/`*Rounded` color each vertex by its own distance from `points[0]`.** Barycentric coordinates aren't well-defined for a general N-gon, so the two use different fixes for the same underlying problem — coloring by "nearest vertex" instead made adjacent fan wedges blend two nearly-identical colors against one different one, visible as radial creases on a rendered star.
- **Shape-family gaps were closed by auditing the full Fill/Border/Draw matrix against itself, not by guessing what's missing.** This pattern (find a shape family missing a sibling a peer shape already has, add it, verify by rendering) filled in: Triangle/Ellipse/Poly/Polygon/Capsule shadows, `FillPolyRounded`/`BorderPolyRounded`/`DrawPolyRounded`, `FillEllipseGradientLinear` (whose `rotation` tilts both the ellipse and the gradient axis together, unlike Circle's, since a circle has no shape-orientation of its own), `CheckCollisionCircleCapsule`/`CapsuleCapsule`, `DrawCircleSectorGradient`/`DrawRingGradient`, `FillPolyGradientRounded`, `DrawCircleSectorShadow`/`DrawRingShadow`, `DrawPolyGradientRounded` (whose first draft clamped a corner radius against the wrong, independently-derived polygon size — rewritten to inset an already-rounded boundary instead), and `FillTriangleShadowRounded`/`FillPolyShadowRounded`/`FillPolygonShadowRounded`. `DrawRingShadow`'s partial-wedge case computes its offset boundary in closed form instead, since a ring wedge's inner-arc corners are genuinely reflex — the same case the shared halo helper gets wrong.
- **`FillRectangle`'s 4-corner-color overload triangulates as 2 triangles sharing the `topLeft`–`bottomRight` diagonal, not true 4-corner bilinear.** A point exactly on that diagonal blends only those 2 corners — caught by a test's own "center equals the average of all 4 corners" assertion failing first. Documented as the real behavior rather than overclaiming bilinear; gained `rotation`/`origin` later, found missing via a gap search against raylib/MonoGame.Extended.
- **2D's private `SampleUnitCircle` was promoted to a public `UnitCircleLut` class**, matching 3D's already-public `TrigLut` — 2D had no equivalent fast-trig tool for a caller's own curved geometry. Its `Sample` floors before casting to an index (matching `Noise`'s lattice-wrap pattern) rather than truncating, which was silently imprecise for negative/out-of-range input.
- **2D `Capsule` (`Fill`/`Border`/`Draw`/gradient) has both an endpoint-pair overload and a `center, length, rotation` overload, kept side by side.** The endpoint form is what the geometry is actually built on; the center form was added to match every other shape's "center + size + rotation" convention. `FillCapsuleGradient`'s "distance from center" is distance from the axis *segment*, not a point — each boundary vertex pairs with whichever pole its own cap arc surrounds.

## 3D shape rendering

- **3D face winding sets the light/cull normal** (`Cross(b-a, d-a)`). Wrong winding is invisible under the default unlit/`CullNone` state but breaks lighting/culling silently — verify winding explicitly for any new filled 3D shape; a flat unlit render proves nothing.
- **Sphere/hemisphere pole quads use an exact outward normal (`point - center`), not the default edge cross-product.** At a pole ring two of the quad's four corners coincide, so the cross-product normal goes zero-length, `Normalize` turns that into NaN, and casting NaN to a byte silently blackened the whole quad — the reported "top of the sphere doesn't light up" bug.
- **`TrigLut.SinCosStep`'s generic interpolation path floors before splitting into index+fraction, same fix as `UnitCircleLut.Sample`.** A raw truncating cast picked the wrong pair of adjacent table entries for negative `step`. While there, added `TrigLut.Sample(t01, ...)` and `SampleRadians`/`SampleDegrees` on both `UnitCircleLut` and `TrigLut`, since `TrigLut` was missing the continuous-angle entry point its own "3D counterpart to `UnitCircleLut`" description implied.
- **3D's spline family (`DrawSplineBasis3D`, `DrawSplineBezierQuadratic3D`, all 4 `GetSplinePoint*3D` functions) was completed to match 2D's.** It was only half-ported before (`CatmullRom3D`/`BezierCubic3D` only) despite the file's own section header already claiming "2D parity." `DrawSplineBasis` is an *approximating* spline (does not pass through its control points), unlike Catmull-Rom — confirmed by rendering both on the same points side by side.
- **`DrawLineStrip3D`/`Trail3D.Draw` used to draw each segment as an independent camera-facing quad, leaving a real gap at shared bends (measured 0.41 units at `thickness=1.5`).** Fixed with a proper joined strip: one offset per *vertex* instead of per segment (an interior vertex miters its two adjacent segments' offsets together, the same shape as 2D's `ComputeMiterOffset` one dimension higher), so both segments touching a vertex read the identical offset by construction. Added a per-segment-color overload (not per-vertex — matches what `Trail3D`'s fade already computes) so `Trail3D` could adopt the same geometry without losing its fade.
- **`ResolveSegments`'s auto-LOD measures distance from the world origin**, not an explicit center — its old doc comment described this unclearly and was fixed to match the real behavior, not a behavior change.

## Input

- **`PrimitiveInput`'s suspected freeze on window drag/resize was investigated and found to not be a library bug.** A full read-through found no blocking calls, loops, or window-event subscriptions; it's almost certainly MonoGame/Windows' own `WM_ENTERSIZEMOVE` behavior — the OS blocks the message pump during a drag, so nothing downstream runs until it ends. Outside any library's control; re-open only with a concrete repro that isn't just "window drag pauses like every MonoGame game."
- **`DragDelta`/`IsDragging` fixed to still report correctly on the release frame.** `_dragStart` used to null the instant the button went up — the same frame `IsMouseButtonReleased` becomes true — so "on release, check how far I dragged" always read zero. Now the reset happens on the *next* press instead, with a snapshot captured at release.
- **`IsMouseButtonDoubleClicked` now also checks `DoubleClickDistance` (6px default), not just `DoubleClickTime`.** Previously two clicks anywhere on screen within the time window counted as a double-click.
- **`ApplyDeadzone` now rescales the surviving range back onto `[0,1]`, not just clamps below the cutoff.** It already used a radial (not per-axis-square) cutoff, but never rescaled past it, so output jumped straight from 0 to ~deadzone's own magnitude instead of ramping continuously — the standard "scaled radial deadzone" half-fix. Made `public static` since the same curve is useful for any analog input this class doesn't read itself.
- **Gamepad gained `SetVibration` (raw, stateless — no built-in duration/timer, a per-game decision), `Left/RightTriggerDeadzoned`, and `IsAnyButtonPressed`.** `IsAnyButtonPressed` deliberately excludes the analog stick/trigger "as digital button" flags MonoGame also reports, so idle drift or a light trigger rest can't misfire it. `IsAnyKeyPressed`/`IsAnyMouseButtonPressed` mirror it for keyboard/mouse.
- **`GetCharPressed()` needed a new `PrimitiveInput(GameWindow)` constructor — confirmed first this genuinely can't be built from `Keys` polling.** A physical key isn't the character a layout/shift/dead-key sequence produces, and even raylib's own equivalent is backed by a real OS character callback, not key-state polling. Subscribes to `GameWindow.TextInput`; the parameterless constructor just never populates the queue, so `GetCharPressed()` returns `'\0'` rather than throwing. The queue is a fixed 64-char ring buffer that drops new input once full rather than growing unbounded. `PrimitiveInput` became `IDisposable` solely to unsubscribe this handler.
- **`SetCursor` and `CapsLock`/`NumLock` were added — plain MonoGame passthroughs that had simply never been wrapped.** Found comparing against raylib/love2d/Godot/Unity's input surfaces. A real "relative/captured" mouse mode does not exist to wrap at all — decompiling MonoGame's `Mouse` class confirmed it has no such API; the manual re-center-every-frame trick this library already supports is the actual ceiling here, not a missing convenience method.

## Color, easing, noise, random

- **`Easing` has every family's In/Out/InOut** (previously inconsistent — Quad/Cubic/Sine had all three, others didn't). `Quint` and `Circ` were added later as the two families missing from the standard Penner/easings.net set, confirmed against raylib/Godot/DOTween all agreeing they belong.
- **`EasingType` + `Easing.Evaluate(type, t)` dispatch by enum, added alongside the 31 named functions rather than replacing them.** A curve is usually known at compile time (call `CubicOut` directly), but not always — a curve chosen from a config/level file or a debug-UI dropdown needs to be data, and a bare `Func<float,float>` isn't serializable/inspectable the way an enum value is. Matches the shape Godot (`Tween.EaseType`) and DOTween both expose alongside their own named-function APIs.
- **`ColorUtil.FromTemperature(kelvin)` uses Tanner Helland's polynomial fit to the CIE blackbody locus**, not a physically exact spectral calculation — the standard approximation for fire/plasma/heatmap coloring, cheap and good enough for that use case. Verified at reference points a blackbody curve must hit: ~1000K comes out red-dominant with zero blue, ~6600K comes out roughly neutral (R≈G≈B), 20000K comes out blue-dominant — a real check, not just trusting the formula.
- **`RectangleF.Lerp` doesn't clamp `t`** (matches `MathHelper.Lerp`'s own behavior, confirmed no clamping) — extrapolating past `[0,1]` is occasionally useful (overshoot easing) and clamping can always be applied by the caller, but an implicit clamp can't be un-done once baked in.
- **`Noise.Sample1D` has its own dedicated 1D gradient, instead of slicing `Sample3D` at y=0,z=0.** `Sample2D` slicing at z=0 is fine (x and y stay free variables), but fixing both y and z to 0 zeroed several of the hash table's cases — measured ~23% of samples landing near zero (vs. ~2% expected), an 11x inflation reading as visibly flatter output than documented. Dropped to ~3% with a proper dedicated gradient.
- **`Noise`'s `octaves`/`lacunarity`/`gain` moved from per-call parameters to instance properties**, matching this project's own established shape for tunable knobs (`Camera2D.MoveSpeed`, etc.) rather than repeating the same three values at every call site. `RidgeNoise`/`Turbulence` were added as alternate octave-combination formulas over the existing samples (confirmed against Godot's `FastNoiseLite`/`stb_perlin.h`) — not new noise *types* (Simplex/Cellular/domain-warping), which stays out of scope as a whole separate multi-algorithm engine.
- **`ColorUtil` blend modes (`Multiply`/`Screen`/`Overlay`/`Additive`) are pure `Color x Color -> Color` functions**, not a GPU blend-state operation — `Primitive2DBatch` already uses one blend state throughout. Alpha always comes from the first argument in every mode (these blend color, not transparency). `Invert`/`Contrast` were added later as the two real gaps found comparing against raylib/love2d/Godot/Unity; everything else considered already exists on MonoGame's own `Color` struct.
- **`Palette.GradientPairs` (inner/outer color pairs for `FillCircleGradient`'s glossy look) is a curated 6-entry subset, not exhaustive** — meant to grow, not the final word on which colors.
- **`RandomUtil` (seedable distribution sampling) was added for the simulation use cases `PROJECT.md` already names** — predator-prey, pandemic models, cellular automata. Gaussian uses Marsaglia polar, not Box-Muller, to avoid any `Sin`/`Cos` call on a hot path; Poisson/Binomial switch to a Gaussian/Poisson approximation above a threshold rather than simulating directly, since both are otherwise unbounded-cost per sample. Circle/sphere sampling uses plain `MathF.Sin`/`Cos` deliberately, not `UnitCircleLut`/`TrigLut` — those live in the 2D/3D namespaces, and Core (which 2D/3D both depend on) reaching back into either would invert that dependency.
- **`RandomUtil.Shared` is a static, genuinely thread-safe mirror built on `Random.Shared`.** The instance API stays single-threaded on purpose (one stream per instance, same assumption `Noise`/`PrimitiveInput`/the cameras make) — parallelizing a sim should give each thread its own seeded instance, cheaper than locking and just as reproducible. `UnderlyingRandom` exposes the wrapped `Random` directly (sharing the same stream, not a second desynced one) for anything this class doesn't itself wrap — added after a real gap surfaced: a caller could only reach methods this class chose to expose, never `Random`'s own surface. `NextWeightedIndex` was added as the one real gap found comparing against Godot's `RandomNumberGenerator.rand_weighted_pick`. `NextItem<T>` (uniform pick from a `ReadOnlySpan<T>`) and `NextGaussianVector2`/`3` (per-axis `NextGaussian`, for scatter/jitter around a point) round out the same "what a sim/prototype reaches for constantly" gap analysis.
- **`Vector2Extensions` benchmark confirmed no real performance difference between MonoGame's own `Vector2` and `System.Numerics.Vector2`** across common ops and a mixed particle-steering scenario (within noise of each other). Confirms there's no performance case for switching this library's public API off MonoGame's own type — which would be a breaking, ecosystem-wide change regardless.

## Font

- **`FontGlyphs5x7`: `a`/`e`/`g`/`u` (and accented `á`/`é`) were one row taller than every other x-height lowercase letter — fixed.** Every non-ascender lowercase glyph should occupy exactly 5 rows on a shared baseline; these four had one literally-duplicated row in their bitmap data, almost certainly a copy-paste slip when originally authored.
- **Lowercase `h`'s crossbar stopped one column short of its right leg**, reading as a disconnected leg — widened to full width. `n`/`ñ` share the identical flaw and were left unchanged pending confirmation, since only `h` was reported.
- **`FontGlyphs5x7.WrapText` (greedy word-wrap) lives in `Core/`, shared by both namespaces** — `DrawString`/`DrawString3D` gained a trailing `maxWidth` parameter that calls it internally using the exact `pixelSize`/`glyphSpacing` already being drawn with, rather than making callers wrap-then-draw as two separate calls that could silently disagree on those values.

## Testing & tooling

- **`tests/MonoPrimitives.Tests/` is a headless `Game`, not an xUnit project.** `Primitive2DBatch`/`Primitive3DBatch` both need a real `GraphicsDevice`, which MonoGame only creates inside a running `Game` — a standard test runner never gets one. Pure-math checks and GPU-dependent ones both run once from `Draw()`, print a pass/fail summary, and exit 0/1 like a CI step expects.
- **`ShapeTests2D.cs` closed a real gap: 2D had zero automated protection against a shape rendering in the wrong place or size, unlike 3D's smoke tests.** Renders each major shape family to an offscreen target and samples actual pixels (interior = fill color, exterior = background, border-only = unfilled center) rather than just "didn't throw." `PolygonInsetRegressionTests`/`ClearLetterboxedTests` lock in two real bugs (the `InsetConvexPolygon` reflex case, the 0.5.6/0.5.7 double-offset bug) as permanent regressions.
- **`FastTexture` uploads via raw `glTexSubImage2D` instead of `SetData`, falling back to `SetData` transparently when the fast path isn't available.** A first synthetic benchmark found it 2-4x *slower* — an artifact of forcing 10 back-to-back calls with no frame boundary between them, which stalls the GL driver on a resource hazard real per-frame usage never hits. Re-measured with a real per-frame loop: consistently ~2.5-2.7x *faster*.
- **`FrameLimiter` sleeps most of a frame, then busy-spins the last ~2ms.** Measured directly: `Thread.Yield`/`SpinWait`/a plain busy loop are statistically identical for the final stretch. What actually drives precision is whether `Sleep` gets called at all — on Windows, any `Sleep` call has a real ~1-5% chance of overrunning by nearly a full frame, an OS scheduler cost outside this class's control. A pure busy-spin avoids that but pins a full core the whole frame, the wrong tradeoff for a general-purpose library.
- **`FrameLimiter` composes a private `FpsCounter` instead of duplicating its rolling-average math**, fed every `BeginFrame()` with the *raw, pre-`MaxFrameTime`-clamp* frame time — so `AverageFps`/`CurrentFps`/etc. always reflect true achieved performance, including a real stall `MaxFrameTime` clamps down for the caller's own `FrameTime`. Exposed as pass-through properties (`AverageFps`/`CurrentFps`/`AverageFrameTimeMs`/`CurrentFrameTimeMs`/`FpsSampleCount`), not the `FpsCounter` instance itself — same reasoning as `Elapsed` not exposing the raw `Stopwatch`: a caller calling `Update` on a directly-exposed counter would desync it from `BeginFrame`'s own feed. `MaxFrameTime`'s `0` default means "disabled," not "clamp to zero" — the constructor param exists specifically so a frame that took far longer than intended (breakpoint, GC pause, asset load) can be reported as a smaller, simulation-safe value instead of driving one huge simulated step. The very first `BeginFrame()` call has no real previous frame to measure, so it feeds the counter `1/TargetFps` instead of a literal `0` — a phantom zero-duration sample would otherwise inflate `AverageFps` (`filled/sum`) for the next `FpsSampleCount` frames, since it adds a free count with no time cost.
- **Batcher performance was measured end to end with a real per-frame benchmark, not a synthetic tight loop.** Two micro-optimizations kept (a redundant `sqrt` eliminated, `ComputeJoint`'s corner-angle math reduced from two `Atan2` calls to one) even though neither showed a measurable difference, since both are correctness-neutral. The real finding: rounded corners cost ~81% more per-shape than sharp ones, and that cost is inherent to how much more geometry a smooth arc is — not something `ComputeJoint`'s setup or `UnitCircleLut` waste. A later attempt to replace `Cos`/`Sin`/`Atan2` with polynomial approximations was tested with a properly controlled interleaved benchmark and reverted — the effect was within the benchmark's own noise floor, not a real win, and would have traded real (if small) accuracy for nothing confirmable.
- **`ScreenshotUtil.Capture(device, filePath)` fills a real gap: MonoGame's own `Texture2D.SaveAsPng`/`SaveAsJpeg` only save a texture the caller already owns**, not the actual rendered frame — every project was re-writing the same `GetBackBufferData`-to-`Texture2D` boilerplate. Format is inferred from the file extension, matching raylib's own `TakeScreenshot`.
- **`GenerateDocumentationFile` and `Nullable` were enabled project-wide.** Without the first, the ~3,000 lines of `///` comments in this codebase never compiled into a `.xml` file, so every published version shipped with zero IntelliSense for consumers despite the documentation effort already spent. Enabling it surfaced 329 pre-existing doc-comment warnings (mostly `CS1573` — some but not all of a method's parameters tagged), closed in a later dedicated pass: real cref/XML errors fixed by content, the bulk of missing `<param>` tags added with real per-parameter text. `Nullable` surfaced 42 real warnings, all fixed in the same pass — annotations only, source- and binary-compatible.
- **`Primitive2DBatch.Dispose()` gained the same `_disposed`/`ThrowIfDisposed()` guard `Primitive3DBatch` already had.** It used to be a bare call with no guard at all, so using a disposed batch afterward failed opaquely inside an already-released `BasicEffect` instead of a clear error.
- **`CHANGELOG.md` (Keep a Changelog format) was added, backfilled from git history through 0.8.0.** Version history was previously only reconstructable by reading commit messages — no curated release notes existed for a package already published on NuGet. Git tags themselves aren't fully reliable as a source (`V0.1.5`/`V0.2.0`/`v0.2.5` point to commits orphaned by a history rewrite around 2026-08-21 and aren't ancestors of `main`); entries were built from the actual linear history instead, using each `chore: bump package version` commit (or the commit a still-valid tag points to) as the version boundary.
- **CI (`.github/workflows/ci.yml`) builds `src`/`tests`/`samples`/all 13 `examples/` via an expanded `MonoPrimitives.slnx` on every push/PR, plus a separate job for `templates/PrimitiveBase`.** `xvfb-run` supplies the virtual display `MonoGame.Framework.DesktopGL` needs to create a real `GraphicsDevice` on a display-less Ubuntu runner. The template is a separate job on purpose: it resolves the *published* NuGet package, not this commit's source, so a failure there means something different (the currently-pinned version broke) than a failure in the main build.

## Examples & demos

- **`examples/demos/` stopped at 6 games + 1 simulation** (Breakout, Tetris, Asteroids2D, Asteroids3D, Platformer2D, Snake, Boids) — Boids specifically to demonstrate the "simulations" half of this project's scope, since every other demo is a game.
- **`Asteroids3D`'s flight model recomputes the ship's "up" fresh each frame from forward/world-up, rather than accumulating roll into it** — standard rigid-body Euler integration made yaw drift off-axis after any pitch, reported as "controls feel super weird." Roll (Q/E) stays a cosmetic camera bank only, never fed back into flight. Trades true 6DOF tumbling for a controllable arcade feel — the right call for a demo, not a flight sim.
- **`Platformer2D`'s ground check uses a direct float comparison against the platform rectangle, not `Rectangle`-vs-`Rectangle` intersection.** Truncating the player's float position into an integer `Rectangle` meant the truncated rect stayed identical across almost a full pixel of vertical movement, so "grounded" only registered 1 frame in 3 at rest — roughly two-thirds of jump presses landed on a "not grounded" frame and were silently dropped.
- **`Boids`' neighbor search uses a wrap-aware toroidal distance, not plain position subtraction.** The demo wraps positions at the screen edges; a plain subtraction treated boids just past opposite edges as far apart even though they're visually adjacent after wrapping, collapsing the flock into two stationary clumps at the wrap corners.
- **`templates/PrimitiveBase` sets `Camera2D.Offset = Vector2.Zero` at construction**, matching `examples/test/ViewportTest`'s convention (world origin at the screen's top-left) — the default live-tracked offset put the demo's centered circle near the bottom-right corner instead, caught from an actual render. Its `PackageReference` targets the published NuGet package rather than this repo's own source (verified independently via a temporary `ProjectReference` swap), since that's what a real end user's scaffolded project will do.
- **`templates/PrimitiveBase`'s `.config/dotnet-tools.json` was hand-assembled at some point and only declared `dotnet-mgcb`, not `dotnet-mgcb-editor`** (or its `-windows`/`-linux`/`-mac` platform siblings) — `dotnet tool restore` silently succeeded with just the CLI builder, so `Content.mgcb` had nothing to open the MGCB Editor GUI with. Fixed by regenerating the whole project from a fresh `dotnet new mgdesktopgl` scaffold (which declares all five tools correctly) and reapplying this project's customizations (`Game1.cs`, the `MonoPrimitives` reference, `.template.config/template.json`, and the `Exe`/`net10.0` settings that match the rest of `examples/`) on top, instead of hand-editing the broken one further — safer than trying to enumerate everything else a hand-assembled scaffold might be missing.

## Process

- **Render genuinely new geometry before trusting it — the standing verification rule.** This codebase is built mostly by an AI with no live `GraphicsDevice` by default; reasoning alone has missed real bugs here (tangent gaps, self-intersections, inverted normals invisible under flat shading). See CODESTYLE.md.
- **`Guide/*.md` is end-user reference only — no audit narrative, no "this session found X."** An early pass let `Camera3D_Guide.md`/`Primitive3DBatch_Guide.md` drift into narrating the raylib-comparison audit itself; rewritten to keep only user-facing behavior, with that narrative moved to this file. A later full audit (public API vs. what each guide actually documented) found real undocumented members across 10 of 15 guides at the time — `Trail3D` had no documentation anywhere — closed by adding the missing coverage, not by rewriting tone again.
