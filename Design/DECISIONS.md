# Decisions — the *why*, condensed

One line or a short paragraph per decision. Check here before "fixing" something that looks wrong — it might be deliberate. Full narrative (if you ever need it) is in the per-library changelogs; not needed for normal work.

- **Single assembly, not a multi-package split.** `MonoPrimitives.dll`, raylib/MonoGame.Extended-style — explicit preference over separate `Core`/`Primitives2D`/`Primitives3D` packages. Folder layout (`Core/`, `2D/`, `3D/`) is unchanged; only the number of installable artifacts changed.
- **Namespaces unified under one root: `MonoPrimitives`/`MonoPrimitives.Primitives2D`/`MonoPrimitives.Primitives3D`.** Previously `Primitives2D` and `MonoPrimitives3D` were bare top-level namespaces unrelated in name to `MonoPrimitives` (Core) — inconsistent naming (one has no prefix, one has no dot) with no signal they're one package. Nesting both under `MonoPrimitives.*` makes a single `using MonoPrimitives.*;` read as "this project," matches the single-assembly decision above, and is the naming MonoGame.Extended-style libraries use for their own sub-namespaces.
- **No physics resolution, ever.** `Collision2D`/`Collision3D` detect overlaps only; response (push apart, impulses, constraints) is out of scope. A Verlet-based resolution module was built once and deleted for crossing this line.
- **Core-sharing rule:** code identical apart from the namespace goes in `Core/`. Genuinely different code (e.g. 2D vs 3D math) stays duplicated per namespace rather than forced into a shared abstraction. `SpatialHashGrid2D`/`3D` were removed entirely (out of scope), not moved to Core.
- **Antialiasing is MSAA**, a caller-side `GraphicsDeviceManager` setting (see the sample's `PreferMultiSampling`) — not something the library does internally. A screen-space shader post-process (FXAA-style, then a simpler edge-aware blend) was built and verified rendering correctly, but shelved anyway: kept making real content look worse in side-by-side comparison despite passing isolated checks, and MSAA already covers this adequately. Simplicity won over "we already built it." A feathering/`AntialiasedEdges` direction was abandoned earlier for the same reason; either could come back if there's a concrete reason MSAA falls short.
- **`Camera3D` merges camera + controller into one class**, unlike raylib's split — better fit for C#'s OO style. `Camera2D` mirrors the same input-driven-update shape (previously it had no input handling at all — every caller, including the sample, hand-rolled WASD-pan/wheel-zoom/drag-pan from scratch).
- **`Camera2D`/`Camera3D` both take their `ViewportAdapter2D` at construction, not as a per-call parameter.** First pass (2D) added `ScreenToWorld(pos, adapter)`/`WorldToScreen(pos, adapter)`/`ReadDefaultInput(dt, adapter)` overloads — functionally fine, but required passing the same adapter at every call site, and MonoGame.Extended's own `OrthographicCamera(ViewportAdapter)` doesn't work that way. Redone to match, then carried into `Camera3D` for the same reason: a `Camera2D(ViewportAdapter2D, ...)` / `Camera3D(ViewportAdapter2D, ...)` constructor stores it on a `ViewportAdapter` property, and every viewport-dependent method reads that stored reference instead of taking one as an argument — `ScreenToWorld`/`WorldToScreen`/`GetVisibleWorldBounds`/the mouse-drag part of `ReadDefaultInput` on the 2D side; `GetWorldToScreen`/`GetScreenToWorld`/`GetScreenToWorldRay` and `Primitive3DBatch.Begin(camera)` on the 3D side (the old `Begin(camera, viewportAdapter)` overload was removed — `Begin(camera)` alone now does `camera.ViewportAdapter?.Apply()` first). `Camera2D.Offset` defaults to the adapter's virtual center (Extended's convention) but stays a plain mutable field, so callers that want a different anchor (e.g. this project's own 2D gallery, which wants `Offset = Vector2.Zero` so `Target` is the world point at the screen's top-left corner) just set it back after construction — no separate code path needed.
- **`Camera3D.Reset()` + `R` binding.** Restores Position/Target/Up/Fovy/Projection/near/far to the values passed at construction and clears zoom/follow/head-bob smoothing state, bound to `R` in `UpdateWithInput`, which returns immediately on the reset frame (skips movement) so a same-frame WASD/mouse delta can't immediately fight it. `Camera2D` has no equivalent yet — not asked for on the 2D side.
- **`Primitive3DBatch.Begin(Camera3D, ViewportAdapter2D)` overload.** Plain `Begin(camera)` always projects using `Device.Viewport.AspectRatio` — correct only if nothing has narrowed the device viewport. A 2D layer letterboxed via `BoxingViewportAdapter2D` never touches `Device.Viewport` itself unless something calls `Apply()`, so a 3D scene sharing the same window as boxed 2D content would silently project against the full backbuffer and stretch into the bars. The new overload just calls `viewportAdapter.Apply()` then delegates to the existing `Begin(camera)` — no separate 3D-specific viewport math needed, since `ViewportAdapter2D`'s `BoundingRectangle` is exactly the on-screen sub-rect a 3D projection needs too. See `Design/2D/ViewportAdapter_Guide.md`.
- **`PrimitiveInput` reviewed for a suspected freeze on window drag/resize/close — no bug found, not re-investigated without a repro.** Full read-through of `PrimitiveInput.cs`: no blocking calls, no loops, no window-event subscriptions of any kind (nothing hooks `Activated`/`Deactivated`/`Exiting`/`ClientSizeChanged`) — confirmed by grepping the whole `src/` tree for blocking primitives (`Thread.Sleep`, `.Wait()`, `lock`, `while(true)`) and window-lifecycle event names, both empty. The freeze this was reported against is almost certainly MonoGame/Windows' own `WM_ENTERSIZEMOVE` behavior — the OS blocks the message pump during a window drag/resize, so `Game.Tick()` (and everything downstream, including this library) simply doesn't run until the drag ends. That's outside any user-level library's control; the usual workarounds (tick from a separate thread/timer) are out of scope for a primitive-drawing library. If a concrete repro shows up that isn't just "window drag pauses like every MonoGame game," re-open this.
- **`Collision3D.GetRayCollisionBox`'s face-normal detection rewritten from fixed-epsilon to nearest-face selection.** Found during a full utilities audit (`Design/README.md`'s 5 docs don't cover this level of detail; noted here since it's non-obvious). The old code checked each of the 6 face planes with a hardcoded `1e-3` absolute epsilon, falling through to a hardcoded `+Z` normal if none matched. Empirically confirmed broken at scale: a 1,000,000-unit box with oblique rays returned the wrong (always the hardcoded fallback) normal on ~7% of hits, because floating-point error in the hit-point computation at that scale (0.03–0.12 units) routinely exceeds a fixed 0.001 epsilon even for a geometrically unambiguous mid-face hit (next-nearest face tens of thousands of units away). Fixed by computing the distance to all 6 face planes and picking the minimum — scale-invariant, no epsilon to tune. Verified: 0/2000 wrong normals after the fix, same test.
- **`Noise.Sample1D` given its own dedicated 1D gradient instead of slicing `Sample3D` at y=0,z=0.** Also found during the utilities audit. `Sample2D` slicing `Sample3D` at z=0 is fine (both x and y stay free variables, so `Grad`'s 12-direction table always has a nonzero-contributing term) — but `Sample1D` fixed BOTH y and z to 0, and several of `Grad`'s hash cases route their x-facing component through `y` or `z` instead of `x`, so those cases evaluated to exactly zero. Empirically confirmed: ~23% of samples landed within 0.01 of zero (vs ~2% for `Sample2D`, the expected rate for real noise) — an 11x inflation, i.e. visibly flatter/steppier output than the class's own docs promise ("a smooth, deterministic wander," explicitly for things like wind-gust strength). Fixed with the standard dedicated 1D gradient (±1 selected by a hash bit). Verified: near-zero rate dropped to ~3%, in line with `Sample2D`'s.
- **`PrimitiveInput.DragDelta`/`IsDragging` fixed to still work on the release frame.** `_dragStart` used to be nulled the instant a button went up — same frame `IsMouseButtonReleased` becomes true — so the natural "on release, check how far I dragged" pattern always read zero. Now `_dragStart` only resets on the *next* press; a `_dragEnd` snapshot is captured once, right at release, so `DragDelta` keeps reporting the completed drag's distance until the next press starts a new one. `IsDragging` explicitly requires `IsMouseButtonDown` too, so it doesn't inherit that persistence (its own doc says "while held").
- **`IsMouseButtonDoubleClicked` now also checks `DoubleClickDistance` (default 6px), not just `DoubleClickTime`.** Previously two clicks anywhere on screen within the time window counted as a double-click.
- **`Easing` given every family's In/Out/InOut** (`QuartInOut`, `ExpoInOut`, `BackInOut`, `BounceIn`/`InOut`, `ElasticIn`/`InOut`) — previously inconsistent (Quad/Cubic/Sine had all three, others didn't), standard Penner formulas.
- **2D's private `SampleUnitCircle` promoted to a public `UnitCircleLut` class**, matching 3D's `TrigLut` being public — a 2D user had no equivalent fast-trig tool for their own curved geometry. `PrimitiveBatch` now delegates to it instead of keeping a duplicate table. `UnitCircleLut`'s 512-entry table and single `Sample(t01)` API and `TrigLut`'s 1024-entry table and `SinIndex`/`CosIndex`/`SinCosStep` API are left genuinely different, not unified: 2D's circles are typically screen-sized (hundreds of pixels), 3D's are frequently much larger world-space radii needing finer angular resolution, and `TrigLut`'s split sin/cos accessors exist because 3D's sphere/cylinder/torus tessellation samples sin and cos at unrelated angles far more often than 2D's simpler circle walk does. Matching APIs here would mean forcing one's use pattern onto the other for a resemblance with no real benefit.
- **2D's ray checks (`Collision2D.CheckCollisionRay*`) return `bool` + `out` params; 3D's (`Collision3D.GetRayCollision*`) return a `RayCollision3D` struct.** Deliberately not unified into one shape: a 3D raycast commonly needs to compare `Distance`/`Normal` across several candidate hits (which face of a box, which of many objects is nearest) before deciding what "the" hit is, so bundling the result into one reusable, comparable struct pays for itself; 2D's checks are almost always used as an immediate yes/no gate (did the mouse click this circle) where the extra allocation-free `out` params are already the lighter-weight fit. Naming follows the same split: `Check*` for the 2D yes/no gate, `Get*` for 3D's "get me the result struct."
- **`Palette.GradientPairs` added**: inner/outer color pairs for `FillCircleGradient`'s glossy "juicy ball" look, a different flavor from the flat UI colors above. User-supplied palette code (a "fruit merge" game's ball colors) was the direct inspiration; a curated 6-entry subset for hue variety, not the full set — meant to grow, not meant as the final word on which colors.
- **`Fill*Shadow` (drop shadows) built as one vertex-colored ring around the shape's own boundary, not literal 9-slice (9 independently-scaled pieces).** A shader-based blur was ruled out already (see the antialiasing entry below — same reasoning: keep it simple, no shader). The ring approach: solid shape fill (reusing `FillRectangleRounded`/`FillRectangleChamfer`/`FillCircleGradient` exactly, so there's never a seam) plus a halo built from `OutsetConvexPolygon` (new — `InsetConvexPolygon`'s mirror image, same miter-offset math, picks the point *farther* from centroid instead of closer) tracing the shape's own already-generated boundary (`GenerateRoundedRectBoundary`/`GenerateChamferRectBoundary`) outward by `spread`, opaque at the boundary fading to alpha-0 at the outer edge. Because it traces the real boundary instead of scaling fixed corner/edge sprites, it automatically supports per-corner radius, rotation, and chamfer with zero extra bookkeeping — whatever `FillRectangleRounded` can draw, its shadow matches exactly. `FillCircleShadow` is a thin `FillCircleGradient` wrapper (radial gradient already does exactly this).
- **`Camera2D`/`Camera3D` split into two `Update` tiers: `Update` (no input) and `UpdateWithInput(PrimitiveInput, float/GameTime)` (built-in WASD/mouse controller, reading a caller-owned `PrimitiveInput`).** Previously the plain `Update(float)` *was* the input-reading one — convenient, but meant there was no way to use the camera without its built-in movement (e.g. a fixed camera the game code drives directly, or a controller the game defines itself) without also silently getting WASD/mouse-drag baked in. `Update(float)` was redefined as a truly passive tick (decays shake trauma, settles in-flight `SmoothZoom` easing, touches nothing else); the old input-reading behavior moved to `UpdateWithInput`.
- **`CameraInput`/`CameraInput2D` structs and the `ReadDefaultInput`/`Update(in CameraInput[2D], float)` split were removed** — `UpdateWithInput(PrimitiveInput input, float deltaSeconds)` now reads keyboard/mouse straight from `input` and applies movement inline, no intermediate struct. Rationale: this project's own scope explicitly excludes action-based input mapping (see the scope note below), and the struct-building indirection was solving a problem — decoupling input source from camera logic for replays/networking/tests — this library was never trying to solve; every real caller just wanted "read my `PrimitiveInput`, move the camera." Passing the caller's own `PrimitiveInput` instance in (rather than each camera owning a private one) also means one session's input state drives UI, gameplay and the camera without three separate pollers stepping on each other's delta tracking — `UpdateWithInput` deliberately never calls `PrimitiveInput.Update` itself, only reads it; the caller updates it once per frame and hands the same instance everywhere.
- **`Camera3D`'s right-drag mouse-look and Q/E rebinding.** Mouse-look used to add `MouseDelta` directly to yaw/pitch — mathematically an FPS "steer the direction you push" convention, but this camera's look is gated behind holding a mouse button and dragging, which reads more like "grab the world and drag it" (the convention `Camera2D`'s own left-drag pan already uses, via a `-=`) — confirmed by feel, not just theory, since `Yaw`/`Pitch`'s sign convention was independently verified correct against their own doc comments (positive `Yaw` turns left, positive `Pitch` looks up) via a scratch test before touching anything, ruling out a MonoGame-handedness mixup as the cause. Fixed by negating just the mouse contribution (`yaw -= mouseDelta.X * sensitivity`), leaving arrow-key look untouched since only the mouse drag was reported as backwards. Separately, Q/E moved from roll to yaw (rotate the camera's body left/right, alongside the existing arrow-key yaw) since that's the more commonly reached-for binding next to WASD; the old roll behavior moved to Z/X.
- **`Camera2D` has no parameterless constructor — use `CreateDefault()` instead**, mirroring `Camera3D` (which has never had one, only `CreateDefault()`). A bare `new Camera2D()` was the one asymmetry between the two: harmless as a field-initializer placeholder, but an invisible zero-arg constructor doesn't communicate "this is a placeholder, not a real setup" the way a named factory does.
- **Internal batch helper naming unified across 2D/3D**: `PrimitiveBatch`'s `EnsureStarted`/`_isStarted` renamed to match `Primitive3DBatch`'s `ThrowIfNotBegun`/`_began` (better fit — both classes' public API already calls the paired verb `Begin`/`End`, "started" matched no public method name); `Primitive3DBatch`'s `EnsureSpace`/`EnsureSpaceLine` renamed to match `PrimitiveBatch`'s `Reserve` (fewer call sites to touch, and "reserve" already appeared in `Primitive3DBatch`'s own doc comments). Two separate libraries merged into one assembly early on (see the single-assembly decision above) and these pairs were never reconciled until this pass; grepped for other divergent pairs doing the same job — none found beyond these two and a `_disposed`/`ThrowIfDisposed` guard that only `Primitive3DBatch` has (a behavior gap, not a naming one; left alone here, worth a look if `PrimitiveBatch` ever grows unmanaged resources of its own).
- **Trauma-based screen shake on both cameras** (`AddTrauma`/`Trauma`/`GetShakeOffset`, baked into `GetTransformMatrix`/`GetViewMatrix`). The standard technique (Squirrel Eiserloh's GDC talk, used by Celeste etc.): trauma in [0,1] jumps up on impact and decays linearly, but shake *magnitude* scales with trauma² so the falloff itself feels natural (small bumps barely shake, big hits shake hard) — verified exactly: trauma 1.0 and 0.5 gave offset magnitudes in an exact 4:1 ratio. Sampled from this library's own `Noise` (Perlin), one channel per axis (plus one for rotation/roll), instead of raw random, so consecutive frames drift smoothly instead of jittering. Purely cosmetic — baked into the transform/view matrix only, never touches `Target`/`Position`/`Rotation` themselves, so game logic reading camera state never sees it. 3D applies the offset along the camera's own right/up axes (not world axes) so it reads as camera shake regardless of facing direction. Bug found and fixed while verifying this: the noise-time field defaulted to `0f`, and Perlin noise is exactly 0 at every integer lattice point by construction — so the very first shake read after `AddTrauma` (before any `Update` tick) was silently zero; fixed by seeding it to a non-integer value instead.
- **Blend state defaults to `NonPremultiplied`, not `AlphaBlend`.** Every color in this codebase is straight (non-premultiplied) RGBA. `AlphaBlend` expects premultiplied input — feeding it straight color renders translucency far too opaque (verified: alpha 0.15 rendered as ~0.82). If you ever need `AlphaBlend` for a specific draw, premultiply the color yourself first.
- **3D face winding sets the light/cull normal** (`Cross(b-a, d-a)` in `PushQuadLit`/`PushTriangleLit`). Wrong winding is invisible under the default (unlit, `CullNone`) but breaks lighting/culling. Verify winding explicitly for any new 3D filled shape — a flat unlit render proves nothing.
- **Sphere/hemisphere pole quads use an exact outward normal (`point - center`), not the edge cross-product `PushQuadLit` derives by default.** At a pole ring two of the quad's four corners coincide (`FillSphereEx`'s `ry0`/`ry1` or `FillHemisphere`'s `ringRadius`), so the cross-product normal goes zero-length; `Vector3.Normalize` turns that into NaN, and `Shade` casting NaN to a byte silently blackens the whole quad — the reported "top of the sphere doesn't light up" bug. Fixed via a `PushQuadLit` overload taking an explicit normal.
- **No `Ex`/`V`-suffixed method siblings — every parameter variant is an overload of the same name.** `FillSphereEx`/`FillCylinderEx`/`FillCubeV`/etc. were folded into `FillSphere`/`FillCylinder`/`FillCube` overloads (distinguishable by argument types/count, so no ambiguity). `Fill`/`Border`/`Draw` per shape is the naming surface — a different parameter list is a new overload, not a new name.
- **`FillTriangleGradientRounded`/`DrawTriangleGradientRounded` color each rounded-boundary point by exact barycentric weight against the true triangle, not by nearest-original-vertex.** A rounded triangle gradient is still just 3 fan triangles sharing the original `boundary[0]`-ish apex; coloring by "nearest vertex" (flat per-corner color, `FillPolygonGradientByNearestVertex`'s approach) makes each thin fan wedge blend two *nearly-identical* colors against one *different* one, which shows as visible radial creases converging on the apex — confirmed by rendering and sampling a scanline (0 monotonicity reversals after the fix, versus visible banding before). Barycentric coloring reproduces the exact same continuous gradient `FillTriangle`'s single GPU-interpolated triangle has, because barycentric weights are affine and agree across any triangulation of the same triangle. Barycentric coordinates aren't well-defined for a general N-gon, so `FillPolygonGradient`/`FillPolygonGradientRounded` use a different, N-gon-appropriate fix instead — see the next entry.
- **`FillPolygonGradient`/`FillPolygonGradientRounded` color every vertex by its own distance from `points[0]` (normalized against the farthest point), not a binary "`points[0]` gets `from`, every other vertex gets `to`".** The binary scheme meant only the few triangles actually touching `points[0]` in the fan showed any blend at all — every other wedge was flat-`to`-colored — which reads as visible facet seams on a many-sided shape (confirmed by rendering a 5-point star: creases cutting across it). `ComputeDistanceGradientColors` gives every vertex a distinct, smoothly-varying color instead, cutting adjacent-sample color jumps on an inner ring from constant creasing down to 1/179 (residual, not a seam). Both methods also gained the same `IsConvex`/`TriangulateEarClipping` split `FillPolygon` uses (including inside `FillPolygonGradientByNearestVertex`'s own triangulation, for the *Rounded* variant) — a concave shape's fan-from-`points[0]`/`boundary[0]` has the same wrong-topology risk regardless of whether the fill is a solid color or a gradient.
- **A `Border*`'s round/bevel `jointRadius` is capped by its own thickness on a sharp corner — not a bug, a self-intersection guard.** For an inward-only stroke, `ComputeJoint`'s fillet can't reach further than roughly `thickness × cos(halfAngle)` before it would cross the shape's own opposite edge; requesting a much larger radius on a thin border and a sharp point (e.g. a 5-point star's ~42° tips) silently clamps down to a few pixels — correct, but easy to mistake for "the join isn't working" in a screenshot. Verified by reproducing `ComputeJoint`'s math standalone and by rendering `DrawLineStrip` (a symmetric, non-inward-only stroke) with the same three join types: Miter/Round/Bevel produced clearly different, correct results (a 7px/25px/33px difference in how far a sharp corner's spike reached) once thickness was large enough for the difference to be more than a couple of pixels.
- **`FillPolygon` now ear-clips instead of always fan-triangulating.** The fan-from-`points[0]` needed vertex order to sweep monotonically in angle from `points[0]` — a plain 5-point star's outer tip CAN see the whole star (a real "star-shaped from that vertex" kernel point) but its alternating outer/inner vertex order still doubles back angularly as seen from that tip, so the naive fan produced overlapping-and-gapping triangles (confirmed by rendering: a torn chevron, not a star) — visibility alone wasn't the right test. `IsConvex` (O(n), one pass of consecutive-turn cross products) now gates which path runs: convex or triangle input keeps the original zero-allocation fan (no behavior/perf change for the common case — rounded-corner boundaries, regular polygons, etc.); anything else goes through `TriangulateEarClipping` (standard O(n²) ear-clipping over a `prev`/`next` index list, winding-aware convex/reflex test, `PointInTriangle` guard against a remaining vertex poking into a candidate ear). Verified by rendering a 5-point and an 8-point star and probing tips (filled) vs valleys (empty at outer radius, filled at inner radius) — both correct — plus a convex-hexagon regression check confirming the fast path's pixel count is unchanged. Still requires a *simple* (non-self-intersecting) polygon; that case falls back to the old fan rather than drawing nothing.
- **`BorderRing`'s two arcs are drawn as one joined `DrawLineStrip` (`LineJoin.Round`), not one `DrawLine` per segment.** Independent per-segment lines each get their own flat, perpendicular end cap; those caps don't line up on a curve, and once `thickness` is more than a pixel or two the ring reads as a sawtooth of small tick marks instead of a smooth arc (confirmed by rendering: the joined-strip version has zero radial spikes past the expected outer radius, checked at every degree around the ring; the old per-segment version did not). A partial ring's wedge (arc + 2 radial closing edges) is one single closed `BuildOutlineGeometry` loop, not 2 open strips plus 2 separate `DrawLine` calls — 4 independently-rasterized primitives that only *touch* at a shared edge don't reliably rasterize with zero gap even when the underlying math agrees exactly (confirmed by scanning the rendered wedge's boundary for stray transitions: 8 before, 2 — start and end of the one real gap — after). Same lesson applied to `DrawCircleSectorLines`'s two radial edges: they used to be 2 independent `DrawLine` calls sharing only their start point at `center`, leaving an uncovered wedge at that apex (each line's own flat end cap is oriented to its own direction, so the two don't tile) — now one `DrawLineStrip([a, center, c], ...)` with a real joint there.
- **`BuildRoundedOutlineGeometry`'s segment quads must pick `TangentIn`/`TangentOut` vs `InnerCorner` based on that joint's own `Side`, not always "outer=Tangent*, inner=InnerCorner".** A joint's `Side` flips per-vertex with the turn direction (e.g. opposite at a "peak" vs the following "valley" of a zigzag) — when `Side` is negative, `TangentIn`/`TangentOut` actually land on the physical side the segment loop's non-joint fallback (`sideA`/`sideB = 1`) assumes is *inner*. Using them unconditionally as "outer" produced a self-intersecting (bowtie) segment quad — a real gap/crack cutting across the stroke on **any open polyline whose turn direction alternates** (a zigzag/wave being the simplest case) with `LineJoin.Round`/`Bevel`. Confirmed two ways: rendering an open zigzag `DrawLineStrip` showed the crack and a perpendicular scan across the cracked segment found a real background gap between two solid runs (not a single run); a standalone reproduction of the exact quad corners gave a shoelace signed area of exactly 0 (the classic self-intersecting-quad signature) before the fix, and a clean non-crossing quad after. Fixed by swapping which of `TangentIn`/`TangentOut`/`InnerCorner` plays "outer" vs "inner" per joint based on that joint's `Side` sign. Closed shapes (`BorderPolygon`/`BorderTriangle`/etc.) go through the same code but weren't hit by this in prior testing — re-verified after the fix via pixel-count sanity checks on an L-shape and a star border, no regression.
- **`ComputeJoint`'s rounded-corner clamp is per-corner, not per-edge** — two adjacent corners can together claim over 100% of a shared edge before either individually hits its own 90% cap. `ClampCornerRadiusToFit` pre-clamps the requested radius before `ComputeJoint` runs, rather than changing `ComputeJoint`'s shared constant (used by many already-verified callers).
- **Never name "raylib" (or other design inspirations) in doc comments or user-facing docs.** Standing rule — see CODESTYLE.md.
- **Grid/heatmap rendering: texture-backed (`SetData` + one scaled draw), not per-cell `FillRectangle`.** Measured on a 2048×2048 grid: full-texture `SetData` ≈5.2ms, draw-only ≈0.004ms; `FillRectangle` scales linearly with *visible* cell count (~558ms at 100% visible, ~3.2ms at 1%). Crossover is ≈1% of the grid visible — texture wins for any normal "zoomed out enough to see structure" view, more so if the data updates slower than render rate. Built as `GridRenderer2D` (`SetCell`/`Fill`/`Apply`/`Draw`) — a separate class from `PrimitiveBatch`, not a mode of it, since a textured quad is a genuinely different rendering path from `PrimitiveBatch`'s deliberately texture-less vertex-colored triangles. Defaults to `SamplerState.PointClamp` (crisp per-cell blocks) rather than the smoothed look linear filtering gives.
- **`tests/MonoPrimitives.Tests/` is a headless `Game`, not an xUnit project.** `PrimitiveBatch`/`Primitive3DBatch` both need a real `GraphicsDevice` (`BasicEffect`, `DrawUserPrimitives`), and MonoGame only creates one inside a running `Game` — a standard test runner never gets one. So the pure-math checks (`Collision2DTests`/`Collision3DTests`/`NoiseTests`/`ColorUtilTests` — no device needed) and the GPU-dependent ones (`ShapeTests3D`, `LightingRegressionTests` — one call per public 3D shape method, asserting it actually emitted triangles/lines without throwing) all run once from `TestRunnerGame.Draw()`, print a pass/fail summary, and exit with the process code a CI step would check (0/1). Two of `Noise`/`Collision3D`'s regression tests directly encode bugs found and fixed earlier this project (`Sample1D`'s degenerate near-zero rate, `GetRayCollisionBox`'s scale-dependent normal) so they can't silently regress. Running the completed suite immediately caught one real issue — not in the library, but in the test itself: `DrawPoint3D` was asserted to emit triangles, but it's implemented via `DrawLine3DFast` and emits lines.
- **3D line-stroke methods (`DrawLine3D`, `DrawArrow`, `DrawLine3DDashed`, `DrawSplineCatmullRom3D`, `DrawSplineBezierCubic3D`) take `thickness`, not `width`; `DefaultLineWidth` is `DefaultLineThickness`.** CODESTYLE.md already documents `thickness` as the canonical name ("`thickness` defaults to `1f` on `Border*`/`Draw*`"), and every `Border*`/`Draw*` method in this same file already used it — only the line-drawing family had drifted to `width`, inconsistent with its own neighbors, not a deliberate 2D/3D split. `FillCube`/`BorderCube`/`DrawCube`'s `width` parameters are untouched — those are genuine box dimensions, a different concept entirely. No external callers used the old name (checked before renaming; the library isn't published yet, so this is a good time for it).
- **2D's two `DrawArrow` overloads collapsed into one** (`color` before `thickness`, both with defaults, plus optional `headLength`/`headWidth`) instead of `(start,end,color,thickness=2f)` and `(start,end,thickness,color,headLength,headWidth)` as separate overloads with `color`/`thickness` in a different order from each other. C# requires required parameters before optional ones, and `color` has no sensible default, so `color` before `thickness` was already forced on the simple overload — the detailed overload just hadn't followed suit.
- **`Camera3D.GetScreenToWorld`/`GetWorldToScreen` renamed to `ScreenToWorld`/`WorldToScreen`**, dropping the `Get` prefix to match `Camera2D`'s names for the exact same operation. `GetScreenToWorldRay` keeps its prefix — unlike a plain position conversion, "get a ray" reads naturally as fetching a distinct object. `Camera3D.ClampToBounds` also made public to match `Camera2D.ClampToBounds` (a 3D caller setting `Position` directly had no way to re-apply the clamp).
- **`Plot2D` was removed.** A dedicated charting library (ScottPlot, etc.) will always render better axes/legends/data-scale handling than a primitive-drawing library's bolt-on chart type — not worth maintaining. This library draws shapes; plotting real data belongs elsewhere.
- **Every `examples/` project needs its own `app.manifest` with `<ApplicationManifest>app.manifest</ApplicationManifest>` in the `.csproj`, copied from `samples/MonoPrimitives.Sample/app.manifest`.** Without a manifest declaring `dpiAware`/`dpiAwareness`, Windows treats the process as DPI-unaware: on any display scaled above 100%, the OS renders the window at its logical size and bitmap-stretches the output to fill the physical pixels, softening *everything* uniformly — including `DebugFont5x7`'s pixel-art glyphs — regardless of what the app actually draws. All 13 `examples/test`/`examples/demos` projects were missing this (an oversight when each was scaffolded — only the pre-existing sample had it), reported as "every test looks blurry."
- **`examples/demos/` stopped at 6 games + 1 simulation: Breakout, Tetris, Asteroids2D, Asteroids3D (the required 5.1-5.4), Platformer2D (explicitly requested, to exercise 2D collision/camera-follow/shake together), Snake and Boids (2 original additions — "up to 2 more, stop early if fewer suffice"; Boids specifically to demonstrate the "simulations" half of this project's scope, since every other demo is a game).**
- **`Asteroids3D`'s flight model rotates yaw/pitch around world Up, not the ship's own (drifting) up vector; roll (Q/E) is purely a cosmetic camera bank, never fed back into flight.** The first version rotated yaw around `_shipUp` and let pitch tilt `_shipUp` too (standard rigid-body Euler integration) — reported as "controls feel super weird"; reproduced by combining sustained pitch then yaw and checking whether yaw's rotation axis had drifted (verified: it had — after pitching, a "yaw" no longer turned cleanly left/right, since it was now rotating around a tilted axis). Recomputing `_shipUp` fresh every frame from `_shipForward`/world `Vector3.Up` (never accumulating roll into it) makes yaw/pitch behave predictably regardless of the ship's current attitude — verified via a scratch test: a pure yaw applied while pitched changed `Forward`'s vertical component by exactly 0.0000, versus a real drift under the old scheme. Pitch is clamped to 5° short of straight up/down to avoid `Cross(Forward, Up)` degenerating there. This trades true 6DOF tumbling for a much more controllable arcade feel — the right tradeoff for a demo, not a flight sim.
- **`Platformer2D`'s ground collision uses a float overlap check, not `Collision2D.CheckCollisionRecs(PlayerRect(), plat)`.** `PlayerRect()` truncates the player's float position into an `int Rectangle`; since `PlayerHalfHeight*2` has no fractional part, that truncated rect stays byte-for-byte identical across almost a full pixel of vertical movement. Combined with `Rectangle.Intersects`' strict (non-inclusive) comparison, resting exactly on a platform after landing needed nearly a full pixel of gravity-driven interpenetration before the truncated rect re-registered as touching — confirmed by simulation: `_grounded` cycled false/false/true while standing perfectly still, true only 1 frame in 3, not every frame. Jump only fires on the single-frame `IsKeyPressed` edge, so roughly two-thirds of jump presses landed on a "not grounded" frame and were silently dropped — reported as "jump randomly doesn't work." Switched the movement-resolution overlap check (not the stomp/goal checks, which aren't gated behind a single input edge and don't need it) to a direct float comparison against the platform `Rectangle`'s edges; verified `_grounded` is now `true` on every frame at rest, with a clean jump-up/fall-back-down cycle landing at the exact same Y each time.
- **`Boids`' neighbor search uses a wrap-aware toroidal distance, not a plain position subtraction.** The demo wraps boid positions at the screen edges (same as `Asteroids2D`), but a plain `self.Position - other.Position` treats a boid just past the right edge and one just past the left edge as far apart even though they're visually adjacent after wrapping — confirmed by rendering: the flock piled into two dense, nearly stationary clumps sitting exactly on the wrap corners before the fix, scattered naturally into several moving clusters after switching to a `ToroidalDelta` that picks the shorter path around each axis.
- **`BoxingViewportAdapter2D`/`ScalingViewportAdapter2D.Scale`/`Offset` read `Device.PresentationParameters.BackBufferWidth/Height`, not `Device.Viewport.Width/Height`.** `Apply()` narrows `Device.Viewport` to the letterboxed rect; reading `Scale`/`Offset` again afterward (e.g. from `Camera2D.ScreenToWorld`/`WorldToScreen` later the same frame) recomputed from that already-narrowed size and silently returned a wrong `Offset`. Found via a `ScreenToWorld(WorldToScreen(x))` round-trip test — 30+ px drift before, 0 after. **Separately: never call `Apply()` before drawing with `camera.GetTransformMatrix() * adapter.GetScaleMatrix()`.** `GetScaleMatrix()` already bakes in `Offset`; narrowing the device viewport too physically re-offsets the same amount again on top, so content lands correctly on X but drifts on Y by roughly `Offset.Y` (only visible with a nonzero `Offset`, i.e. `BoxingViewportAdapter2D` — confirmed via a rendered-pixel-centroid check, not just the round-trip math, since the math alone still round-trips consistently even under the double-offset). Both the sample and `ViewportTest` called `Apply()` this way; fixed by dropping the `Apply()` call from the 2D draw path (bars show correctly from just not drawing there, given a full-window `Clear` first) — `Apply()` is still correct as `Primitive3DBatch.Begin(camera)` uses it internally (scale-only projection, no separate `Offset` add).
