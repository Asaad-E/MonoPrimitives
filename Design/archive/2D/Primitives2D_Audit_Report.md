# Primitives2D — Code Audit Report

**Scope:** `Primitives2D.cs` (single file, single class `PrimitiveBatch`). This is the only file present in the project — no `.csproj`, solution file, or README was available for review. Structural conclusions below are inferred from this single file.

**Testing approach:** this project verifies changes manually rather than with an automated test suite, so this report does not include test suggestions.

**Findings:** 7 open (0 Critical, 0 High, 1 Medium, 6 Low) + 4 Critical, 6 High, and 6 Medium items resolved (C1–C4, H1–H6, M1–M5, M7), plus one extra bug found and fixed along the way (`WithAlpha` premultiplication).

**Note on Security:** this is a client-side, single-threaded immediate-mode renderer with no I/O, network, auth, or persistence surface, so classic security categories (injection, auth, crypto) don't apply. The one relevant angle is *input-validation robustness* (can malformed/adversarial parameters crash or silently corrupt rendering) — covered in **C2 (resolved)** and **L6**. C# is memory-safe, so the realistic worst case is an unhandled exception (crash/DoS), not memory corruption.

---

## 1. Project structure (overview)

Everything lives in one `sealed class PrimitiveBatch` mixing two concerns: a low-level immediate-mode batching engine (`Begin`/`End`/`Flush`/`Reserve`/`PushVertex`) and ~30 public shape-drawing methods built on top of it. The internal organization (region comments: Points, Lines, Triangles, Rectangles, Rounded Rectangles, Circles & Ellipses, Sectors & Rings, Polygons, Splines) is logical and easy to navigate, but the file is large for a single translation unit. See **L7**.

## 2. Public API (overview)

The overload pattern (`Draw<Shape>`, `Draw<Shape>Lines`, `float/Vector2` twins) is mostly consistent and matches the raylib-style API the project targets. Specific inconsistencies are itemized as **M1** and **L5**. The three "point-like" primitives (`DrawPixel`, `DrawPixelFast`, `DrawPoint`) have real behavioral differences (1×1 quad, native GPU point, arbitrary-size centered square) that aren't obvious from the names alone — worth clarifying in docs, not renaming, given the "no public API changes without confirmation" project rule. No public method signatures were changed by any fix in this report.

## CRITICAL — all resolved

### [C1] ✅ RESOLVED — Vertex/index buffers never grow, doc was misleading — `[Bug, Docs]`
**Decision:** buffer capacity stays fixed (set once at construction, no dynamic growth) — deliberate, to keep the class simple. `Reserve()` now flushes whenever **either** the vertex buffer **or** the index buffer would overflow (previously only checked vertices). The constructor's doc comment for `initialVertexCapacity` now states plainly that capacity is fixed and that callers drawing very large single shapes should pass a bigger value up front. A single shape that alone needs more than the configured capacity will still throw — accepted as expected, documented behavior, not a bug.

### [C2] ✅ RESOLVED — Silent `short` index overflow — `[Bug]`
**Fix applied:** `_indices` is now `int[]` instead of `short[]`; `PushTriangleIndices` writes indices directly with no cast. The dead `MaxVerticesPerFlush` constant (whose only reason to exist was the `short` limit) was removed. The index-range ceiling is gone; capacity is now limited only by the buffer size chosen, with no silent wraparound.

### [C3] ✅ RESOLVED — `FlushPoint()` allocated a new array every call — `[Performance]`
**Fix applied:** added a `_pointIndices` field, sized like `_verticesPoint` and filled once in the constructor (always `0,1,2,...`, so it never needs rebuilding — only the *count* passed to `DrawUserIndexedPrimitives` changes per flush). `FlushPoint()` now reuses that array; no more per-call heap allocation.

### [C4] ✅ RESOLVED — Zero-length segments produced NaN geometry — `[Bug]`
**Fix applied:** added a shared `SafeNormalize(Vector2)` helper (returns `Vector2.Zero` instead of NaN for near-zero input, using the same `1e-12f` epsilon already used by `DrawLine`). Applied it to every raw `Vector2.Normalize` call in `BuildPolygonOutlineGeometry` (direction-in/direction-out) and `BuildPolylineOutlineGeometry` (edge direction and the interior miter-direction average). Duplicate consecutive points now degrade to a zero-offset vertex at that point instead of poisoning the whole batch with NaN.

## HIGH — all resolved

### [H1] ✅ RESOLVED — `DrawPixelFast` skipped the `EnsureStarted()` contract — `[Bug, API]`
**Fix applied:** added `EnsureStarted();` as the first line, matching every other primitive. Calling it before `Begin()` now throws `InvalidOperationException` like the rest of the API.

### [H2] ✅ RESOLVED — `DrawLineStrip` skipped `EnsureStarted()` — `[Bug, API]`
**Fix applied:** added `EnsureStarted();` as the first line of the 4-argument `DrawLineStrip` overload (the one that actually builds geometry), before the degenerate-input check.

### [H3] ✅ RESOLVED — `DrawPixelFast` silently broke paint order relative to other primitives — `[Bug, Docs]`
**Fix applied:** `Reserve()` (used by every triangle-based draw call) now flushes any pending points first if there are any; `PushVertexPoint()` (used by `DrawPixelFast`) now flushes any pending triangle geometry first if there is any. This means switching between "drawing triangles" and "drawing fast points" always flushes the previous batch before starting the new one, so interleaved calls (`DrawRectangle → DrawPixelFast → DrawRectangle`) now render in the order they were called, matching every other primitive's behavior. `DrawPixelFast`'s XML doc was rewritten to describe this (and to fix the previous broken-English wording) instead of just warning about the old limitation.

### [H4] ✅ RESOLVED — `SegmentsForArc` doc overstated its accuracy for large radii — `[Bug, Docs]`
**Decision:** matching the same "fix the docs, don't change the underlying tuning" approach used for C1, `MaxCircleSegments` itself was left unchanged (raising it is a real perf/quality trade-off that needs a product decision, not something to change unilaterally). The docstring was corrected to honestly state that the ~0.25px bound only holds up to ≈60px radius, and that beyond that the segment count stays capped and the chord error grows roughly linearly (≈1px at r=200, ≈5px at r=1000), with a pointer to raise `MaxCircleSegments` if smoother large circles are needed later.

### [H5] ✅ RESOLVED — Splines drew independent per-segment quads instead of a shared strip — `[Performance, Duplication]`
**Fix applied:** `DrawSplineCatmullRom` and `DrawSplineBezierCubic` now evaluate all their sample points into a `stackalloc`'d `Span<Vector2>` first, then build one shared-vertex strip via `BuildPolylineOutlineGeometry` (the same path `DrawLineStrip` already used) — proper miter joins, roughly half the vertex count, no more overlapping-alpha seams at sample joints for translucent colors. Both methods now also call `EnsureStarted()` directly, since they no longer indirectly validate `Begin()` through per-segment `DrawLine` calls.
**Deliberately left unchanged:** `DrawLineDashed` and `DrawSplineLinear` were reconsidered rather than mechanically "fixed":
- `DrawLineDashed` draws intentionally *disconnected* dashes — joining them into one miter-joined strip would be wrong (it would visually connect segments that are supposed to have gaps), so independent per-dash draws are the correct design here, not a bug.
- `DrawSplineLinear` has the same "independent per-segment `DrawLine`" shape as the two fixed methods and could benefit from the same treatment, but it wasn't one of the originally catalogued H5 call sites — flagging it here as a good candidate for a follow-up, not touched in this pass.

### [H6] ✅ RESOLVED — Undocumented dependency on non-standard `PrimitiveType.PointListEXT` — `[Bug, Structure/Docs]`
**Fix applied:** added an inline comment directly above the `PrimitiveType.PointListEXT` call in `FlushPoint()` explaining that it isn't part of stock MonoGame NuGet packages, that it requires a MonoGame build/fork with `GL_POINTS` support, and what would need to change (`DrawPixelFast`/`FlushPoint` reworked, e.g. falling back to 1×1 quads) if the project ever moves to stock MonoGame. Also added the same note to `CLAUDE.md` under "Tecnologías" so it surfaces in project-level context, not just buried in a code comment.

## MEDIUM — mostly resolved

### [M1] ✅ RESOLVED (redefined) — antialiasing was hard to control across frames — `[API]`
**Original finding:** `DrawLineStrip`'s per-call `feather` override was the only exception to instance-level `AntialiasedEdges` control.
**What was actually done (per direction given):** rather than touching `DrawLineStrip`'s parameter, `AntialiasedEdges` is now reset to `true` at the start of every `Begin()` call. Turning it off (`batch.AntialiasedEdges = false`) now only affects the current `Begin()`/`End()` cycle — the next frame/batch always starts antialiased by default, so callers don't have to remember to turn it back on. Documented on both the property and `Begin()`.
**Note:** the original M1 (per-call `feather` param on `DrawLineStrip` bypassing the instance property) is still technically present and undocumented — left as-is since a different fix was requested for M1 this pass.
**Superseded:** `AntialiasedEdges` and all geometric feathering were removed entirely later in this document — see "Geometric antialiasing (feathering) removed" below. This entry is kept as the historical record of the API that existed at the time.

### [M2] ✅ RESOLVED — `DrawEllipseLines` didn't clamp thickness against radius — `[Bug]`
**Fix applied:** `half` is now `Math.Min(thickness * 0.5f, Math.Min(radiusH, radiusV))`, matching the clamp pattern already used by `DrawRing`/`DrawRectangleLines`. A thickness larger than the ellipse's own radius no longer flips the inner edge to the opposite side (no more bowtie geometry).

### [M3] ✅ RESOLVED — duplicate outline-building algorithms unified — `[Duplication]`
**Fix applied:** `BuildPolygonOutlineGeometry` (closed) and `BuildPolylineOutlineGeometry` (open) were merged into a single `BuildOutlineGeometry(points, thickness, color, feather, closed)`. Both now share one miter/normal computation and one 4-layer (feather-outer, core-outer, core-inner, feather-inner) vertex layout — the closed-polygon math is unchanged (same `dirIn`/`dirOut` per vertex, wraparound neighbors), and the open-polyline case reuses that same formula with a flat-cap fallback at both endpoints (`dirIn = dirOut` at the start/end, i.e. no miter needed at a free end).
**Visible side effect (intentional, worth knowing):** polygon outlines (`DrawPolygonOutline`, `DrawTriangleLines`) now feather **both** the inner and outer edge of the stroke when antialiased, instead of only the outer edge as before — the old algorithm left the inner edge hard/aliased, which was inconsistent with how `DrawLineStrip` already looked. This is a quality improvement, not a behavior regression, but it does mean polygon-outline edges look very slightly different (better) than before.
**Call sites updated:** `DrawPolygonOutline`, `DrawLineStrip`, `DrawSplineCatmullRom`, `DrawSplineBezierCubic`.

### [M4] ✅ RESOLVED — `DrawRing`'s triplicated branches unified — `[Duplication]`
**Fix applied:** replaced the three hand-written vertex-emission branches and three hand-written triangulation branches with a single generic loop over a small `stackalloc`'d layer list (up to 4 `(radius, color)` pairs: outer feather, outer solid, inner solid, inner feather — built once per call based on `feather`/`innerFeather`). The triangulation loop connects every pair of adjacent layers the same way, for any layer count from 2 to 4. Verified index-for-index equivalent to the three original hand-written cases.

### [M5] ✅ RESOLVED — dead fields removed — `[Duplication/Dead code]`
**Fix applied:** removed the unused `_vertexBuffer`/`_indexBuffer` (`DynamicVertexBuffer`/`DynamicIndexBuffer`) fields — they were never assigned or read anywhere.

### [Extra] ✅ RESOLVED — `WithAlpha` didn't premultiply, causing a bright halo on feathered edges (most visible with white) — `[Bug]`
**File/Line:** `WithAlpha`.
**Explanation:** `Begin()`'s default blend state (`BlendState.AlphaBlend`) expects premultiplied-alpha color data (`Blend.One` on the source side). The old `WithAlpha` only scaled the alpha channel and left R/G/B at full brightness — e.g. `WithAlpha(Color.White, 0f)` produced `(255,255,255,0)` instead of `(0,0,0,0)`. Under a premultiplied blend formula, that stray full-brightness RGB still gets added to the framebuffer regardless of the (zero) alpha, producing a visible bright fringe at every feathered edge. The effect is proportional to how far the color's RGB is from black — invisible-ish for black, maximally visible for white, which is exactly the symptom reported.
**Fix applied:** `WithAlpha(c, multiplier)` now returns `c * multiplier`, using MonoGame's `Color * float` operator, which scales all four channels (properly premultiplying) instead of just alpha.
**Impact of the fix:** every feathered edge across the whole library (lines, circles, ellipses, rings, polygon/polyline outlines, rounded rectangles) now fades to true transparent black at its edge instead of fading to "full-brightness-color-but-transparent," fixing the halo for all colors, not just white.

### [M6] `UnitCircleResolution`'s power-of-two invariant has no guard — `[Structure]`
**File/Line:** `UnitCircleResolution` constant; bitwise-AND indexing trick in `SampleUnitCircle`.
**Explanation:** `SampleUnitCircle` relies on `UnitCircleResolution` being a power of two (only a code comment notes the assumption). The constant is defined as an arithmetic expression (`512 / 2`), making it easy for a future edit to accidentally pick a non-power-of-two value.
**Impact:** A future "just bump the resolution for smoother circles" edit could silently corrupt every curved shape in the library.
**Proposed fix:** Add a `Debug.Assert((UnitCircleResolution & (UnitCircleResolution - 1)) == 0, "must be a power of two")` in `BuildUnitCircle()`, or switch to modulo indexing if the performance difference is negligible.

### [M7] ✅ RESOLVED — Spanish comments remain in a couple of spots — `[Docs]`
**Fix applied:** found 6 remaining Spanish comments, all in `DrawEllipseLines` (not `DrawRing` — the M4 rewrite already cleaned up `DrawRing` itself). Translated to English with no wording drift (e.g. `// cerramos el lazo` → `// close the loop`, `// orden: exterior feather → sólido exterior → sólido interior → interior feather` → `// order: outer feather → outer solid → inner solid → inner feather`). No behavior change; verified no Spanish characters remain anywhere in the file.

## IMPLEMENTED FEATURE — Round/Bevel line joins & caps

**Request:** a generic way to get round-jointed outlines instead of the existing miter joins — usable for rectangles, triangles, polygons, and plain lines, including rounded ends.

**Design decisions confirmed before coding:** three join styles (Miter/Round/Bevel, not just two); the Round join's arc gets full antialiasing (feather ring), matching straight-edge quality; `DrawRectangleLines`/`DrawPolyLines` only switch to the new shared-geometry code path when a non-Miter join is explicitly requested, so their default (Miter) behavior is byte-for-byte unchanged.

**What was added:**
- Two new public enums: `LineJoin { Miter, Round, Bevel }` and `LineCap { Butt, Round }`.
- `BuildOutlineGeometry` (the function already shared by `DrawPolygonOutline`, `DrawTriangleLines`, `DrawLineStrip`, and both splines) now dispatches on `LineJoin`: `Miter` keeps the exact original shared-vertex code path (renamed to `BuildMiterOutlineGeometry`, logic untouched); `Round`/`Bevel` go through a new `BuildRoundedOutlineGeometry`.
- **How Round/Bevel work:** each segment becomes its own independent flat-capped quad (factored out of `DrawLine` into a new shared `EmitLineSegment` helper, removing a small duplication in the process). The gap this leaves on the outer/convex side of every turn is bridged by `EmitJoinFan` — a triangle fan around the joint: a full arc sized by the existing `SegmentsForArc` helper for `Round`, or forced to exactly 1 triangle (a flat cut) for `Bevel`. The concave/inner side needs no extra geometry — the two segment quads already overlap there, harmlessly (same solid color), which is the same trade-off already accepted for `DrawEllipse` (see **L4**). Which side is "outer" is picked via the turn's cross-product sign, verified against a worked numeric example for both left and right turns.
- **Caps:** `LineCap.Round` adds a half-circle (`EmitRoundCap`) bulging past each free end of an open line/strip. `DrawLine` gained a `LineCap` overload; `DrawLineStrip` gained both `LineJoin` and `LineCap` parameters.
- **Configurable joint radius (follow-up, revised after a real bug):** the Round/Bevel joint fillet's radius no longer has to equal the line's own half-thickness. Every Round/Bevel-capable method gained a `float? jointRadius = null` parameter — null (default) keeps the original flush-with-the-line behavior, byte-for-byte.
  - **First attempt (wrong):** the initial implementation just planted the join fan's apex at the plain vertex and gave it radius `jointRadius`. That works only when `jointRadius == half`; for any other value the fan's rim no longer lines up with the segment's own edge (they're offset along the same ray by different amounts), leaving an uncovered wedge between the straight segment and the fan. On the user's own repro (`DrawTriangleLines` with `thickness: 80, join: Round, jointRadius: 80`) this rendered as a broken dart/arrow shape with a stray triangular hole, not a rounded triangle — confirmed by rebuilding the exact vertex/index math in a standalone rasterizer and rendering it to a PNG (not just reasoned about on paper).
  - **Root cause:** a stroke join's round fillet needs to stay *tangent* to both adjoining straight edges — like a rounded-rectangle corner radius, not a circle stamped at the corner. That means the fillet's center has to move off the original vertex, and the straight segments have to be trimmed back to the new tangent points, whenever the radius differs from half-thickness.
  - **Real fix:** replaced the single-point fan with a proper tangent-based fillet. For every joint, `ComputeJoint` finds the fillet center on the same bisector the original miter code already used, at the point where a circle of the requested radius is exactly tangent to both segments' outer edges, and returns the two tangent points. `BuildRoundedOutlineGeometry` then builds each segment's quad using those tangent points as its outer corners (`EmitTrimmedSegmentQuad`, replacing the old fixed-rectangle `EmitLineSegment` call there) instead of the plain vertex, so the straight run and the arc always meet exactly, at any radius — verified by re-deriving the construction numerically against a worked 90°/135° example and cross-checking against the rendered PNG.
  - **Clamped, not unbounded:** on a sharp/short corner, the required trim can exceed what the geometry can safely support (the fillet center can drift far enough to cross into the polygon's own hollow interior and self-intersect the opposite wall) — this was the second bug caught during the same rendering pass. `ComputeJoint` now clamps the effective radius per corner: the trim on each side is capped at 90% of that segment's own length, and the fillet center is capped at one stroke half-width away from the vertex. An excessive radius on a short/sharp corner now degrades gracefully to whatever's safe there instead of self-intersecting — same "clamp rather than break" precedent as **M2**.
  - Only affects joins, not `LineCap.Round` end caps (those still always use half-thickness — not in scope for this follow-up).
- All new parameters are optional and default to `Miter`/`Butt`/`null`, so every existing call site compiles and renders identically to before.

**Call sites updated (all with `LineJoin`/`LineCap`/`jointRadius` as new optional trailing parameters, default unchanged):**
- `DrawLine(...)` — new `LineCap` overload.
- `DrawLineStrip(...)` — new `LineJoin`/`LineCap`/`jointRadius` parameters.
- `DrawPolygonOutline(...)`, `DrawTriangleLines(...)` — new `LineJoin`/`jointRadius` parameters (triangle forwards to polygon outline, so this "just worked" once the shared builder supported it).
- `DrawRectangleLines(...)` (all 4 overloads) — new `LineJoin`/`jointRadius` parameters; when non-Miter, builds a 4-point closed polygon and routes through `BuildOutlineGeometry` instead of the original 4-overlapping-rectangles fast path.
- `DrawPolyLines(...)` — new `LineJoin`/`jointRadius` parameters; when non-Miter, samples all N corner points into a `stackalloc` span and routes through `BuildOutlineGeometry` instead of N independent `DrawLine` calls (this incidentally means `DrawPolyLines` with Round/Bevel is the first time this method gets proper joins at all — its Miter/default path still has the same independent-`DrawLine`-per-edge seams it always had, unchanged).

**Verification:** no `.csproj` exists in this project (source-only library, consumed by copying the file into a host project), so it can't be built or run in place. Compiled clean (0 errors, no new warnings) against `MonoGame.Framework.DesktopGL` in a throwaway scratch project as a stand-in. For the geometry itself (no MonoGame `GraphicsDevice`/window available in this environment either), the exact vertex/index math was re-implemented standalone and rasterized to PNGs to actually look at — this is how both the original bug and the interior-self-intersection clamp issue were caught, neither of which was obvious from reading the code or the math alone. Confirmed clean: the user's exact repro (`thickness: 80, join: Round, jointRadius: 80` on a 90°/45°/45° triangle) both unfeathered and feathered, plus `jointRadius: null` (default, must match pre-follow-up output), plus a spot-check at `jointRadius: 50`/`65` to bisect the clamp's trigger point. Still not exercised inside an actual running MonoGame game — worth a manual look there too before shipping, especially for Bevel and for `LineCap.Round` on open strips, which weren't part of this specific repro.

## MAJOR REDESIGN — Fill/Border/Draw API v2 (Stages 0–9 done: shapes + gradients; file split deferred)

**Request:** a full, clean rewrite of the public API — not a patch. Every raylib-style `Draw<Shape>`/`Draw<Shape>Lines` pair replaced by three consistent verbs per shape: `Fill<Shape>` (no border), `Border<Shape>` (border only, growing **inward**, never exceeding the shape's own footprint), `Draw<Shape>` (both). Plus two new rectangle corner treatments (per-corner rounded radius, and a new chamfer/flat-cut variant), rotation support throughout, and a gradient layer to follow on top. Confirmed with the user up front: old methods removed entirely (no `[Obsolete]` shims); `DrawPixel`/`DrawPixelFast`/`DrawPoint` explicitly untouched; Sector/Ring/Lines/Splines stay in their current form (no natural fill-vs-border split). Full design in the approved plan (not reproduced here) — this entry is the as-built record.

### Stage 0 — performance pass on the outline engine (done first, everything else builds on it)
- `SafeNormalize` and the two other double-precision trig call sites (`SegmentsForArc`, the old rotated-rectangle formula) switched to `MathF`.
- `EmitJoinFan`/`EmitRoundCap` (the Round/Bevel join machinery) now sample the existing `SampleUnitCircle` lookup table instead of raw `MathF.Cos`/`Sin` — restores the class's own stated "no trigonometry at draw time" tenet, which this one spot had quietly violated.
- `BuildRoundedOutlineGeometry` rewritten from one-`Reserve()`-per-segment-plus-per-joint (~3N calls for an N-vertex shape) to a two-pass count-then-emit with a single upfront `Reserve()`. Verified by exact arithmetic cross-check between the new counting function (`JoinFanCounts`) and the emission function (`EmitJoinFanRaw`/`EmitTrimmedSegmentQuadRaw`) — term-for-term match; a mismatch would throw an array-bounds exception immediately (fail-fast), not silently corrupt.
- `DrawEllipse`'s fill fan and AA feather skirt unified into one pass (one `Reserve`, `SampleUnitCircle` sampled once per angle and cached instead of twice) — this was the audit's own **L4**, previously left as deliberate simplicity trade-off, revisited now since circles are central to the whole redesign.
- `Begin()` (both overloads) gained `bool antialiasedEdges = true` — sets `AntialiasedEdges` in one call instead of a separate statement after `Begin()`.
- Added the `UnitCircleResolution` power-of-two guard (**M6**, now resolved) — a `Debug.Assert` in `BuildUnitCircle()`, zero cost in release builds.
- Cleaned up all 16 pre-existing nullable-reference-type warnings (`BlendState?`/etc. parameters and the `_saved*`/`_active*` fields, which are genuinely null between construction and the first `Begin()`).

### New shared building blocks
- **`RectCorners`** (public struct): `TopLeft`/`TopRight`/`BottomRight`/`BottomLeft`, implicit `float` conversion for the uniform case. Used for both rounded-rect radius and chamfer size.
- **`ComputeMiterOffset`**: extracted from the inline miter math in `BuildMiterOutlineGeometry` (pure dedup, byte-identical output).
- **`InsetConvexPolygon`**: the primitive behind every `Border*`'s "inward, never exceeds the shape" guarantee. Shrinks a point list inward by a distance, picking between `ComputeMiterOffset`'s two candidate points via whichever is closer to the polygon's centroid — **deliberately winding-independent** (doesn't assume CW/CCW), verified with a standalone test inset-ing a square in both point orders plus a right triangle, all correct. A `Border*` of `thickness` = stroke `InsetConvexPolygon(points, thickness/2)` with that same `thickness`, landing the stroke's outer edge exactly on the true boundary.
- **`GenerateRoundedRectBoundary`** / **`GenerateChamferRectBoundary`**: sample a rounded/chamfered rectangle's boundary (arcs pre-sampled to points, or 2 points per corner for chamfer) into a caller buffer. Both feed the exact same `FillPolygon`(fan)/`InsetConvexPolygon`+`BuildOutlineGeometry`(Miter) pipeline as any other polygon — rounded/chamfer rectangles aren't a geometric special case downstream of boundary generation, which is what keeps the method count from exploding.

### Shape families landed (Stages 2–7), each `Fill`/`Border`/`Draw` (`Draw` has both a same-color and a `fillColor,borderColor` overload)
- **Rectangle** (sharp) — rotation about center or explicit `origin`. `Border`'s fast path (no rotation, Miter) is the original 4-overlapping-rects trick, unchanged; rotated or Round/Bevel routes through `InsetConvexPolygon`+`BuildOutlineGeometry` (this is also a **correctness fix**: the old Round/Bevel rectangle border didn't inset first and could bulge outward past the rectangle — now it can't). Verified visually: rotated fill + inward border band via a standalone rasterize, border stayed strictly inside the true rotated boundary at uniform thickness.
- **Circle** / **Ellipse** — `Border*`'s ring is now genuinely inward (`[radius−thickness, radius]`) instead of the old straddling `[radius∓thickness/2]`. This repurposes the `DrawCircle(center,radius,Color,Color)` slot from "radial gradient" to "fill+border colors" — the gradient moves to `FillCircleGradient`/`DrawCircleGradient` in the gradient stage, called out explicitly so it isn't lost.
- **Triangle** — `BorderTriangle` via `InsetConvexPolygon`, same pattern as Rectangle.
- **Poly** (regular N-gon) / **Polygon** (arbitrary points) — `BorderPoly` replaces the old per-edge independent-`DrawLine` fast path (which left small corner gaps, not a real join) with the same proper-corner outline builder used everywhere else. `FillPolygon` is a **new capability** (arbitrary point list, no prior fill existed) — fan-triangulated from `points[0]`, documented as correct only for convex/star-shaped-from-first-vertex input; no general ear-clipping triangulation implemented (explicit scope limitation, not silently mishandled). Verified with an irregular (non-regular) convex hexagon: clean fan fill, border band precisely inside the boundary.
- **RectangleRounded** — now takes per-corner `RectCorners radius` (was a single uniform float) plus rotation (was none). Verified with the plan's flagged highest-risk case — four wildly different per-corner radii (including one exactly-sharp corner) combined with rotation — rendered correctly: no self-intersection, no gaps, uniform inward border thickness following the rounded outline including around the sharp corner.
- **RectangleChamfer** (**new shape family**) — a rectangle whose corners are cut straight across; `RectCorners chamfer` is how far each cut reaches back along its two edges, per corner. Same architecture as RectangleRounded (boundary generator → fan fill / inset+Miter border), verified with the same per-corner-different-values-plus-rotation stress case.

**Removed:** `DrawRectangleLines`, `DrawCircleLines`, `DrawEllipseLines`, `DrawTriangleLines`, `DrawPolygonOutline`, `DrawPolyLines`, `DrawRectangleRoundedLines`, the old `DrawCircle(center,radius,inner,outer)` gradient overload, the old `DrawRectangleGradient`. Confirmed via full-file grep: no leftover references to any removed name.

**Verification method throughout:** every genuinely new piece of geometry (winding-independent inset, rotation + per-corner radius together, rotation + per-corner chamfer together, arbitrary-polygon fan fill) was reproduced standalone and rasterized to a PNG to actually look at, not just reasoned through — the same discipline the join-radius bug (above) showed was necessary. Every stage compiled clean (0 errors, 0 warnings) in the throwaway `MonoGame.Framework.DesktopGL` scratch project before moving to the next. File is at 2184 lines (was ~1770 before this redesign); the planned partial-class file split was deliberately deferred until after all shape families land, since splitting a still-mostly-original file has no benefit yet.

### Stage 9 — Gradients (`Fill*Gradient`/`Draw*Gradient` per shape; `Border*Gradient` explicitly out of scope)

Confirmed rule: a `Draw*Gradient`'s fill region stops exactly where its border begins (e.g. circle radius 100, thickness 10 → fill runs 0→90; an `outerOffset` of 20 on top of that starts its solid margin at 70, not 80 — measured from the *inner* boundary, not the full radius). `innerOffset`/`outerOffset` hold solid color for that many pixels before the fade starts / after it ends, scaled down proportionally if they'd overlap (same "clamp gracefully" precedent as **M2**).

- **Circle / Ellipse** — `FillEllipseGradient` (root impl, `FillCircleGradient` forwards) builds a 1–3 "ring" list (inner solid disc if `innerOffset>0`, the gradient ring, outer solid ring if `outerOffset>0`) and fans/bands between them, reusing a single cached `SampleUnitCircle` sample per angle across all rings (same caching discipline as Stage 0's ellipse fix). Verified with a dedicated render: solid blue disc / smooth blue→red band / solid red ring, boundaries exactly where computed.
- **Rectangle** — `FillRectangleGradient` builds a 2–4 "stop" list along the fade axis (H or V) and emits independent quad strips between consecutive stops — same structure as the ring list, just linear. `Draw` insets the fill rect by the full `thickness` on every side first.
- **Triangle** — `FillTriangleGradient` is a one-line wrapper over the existing per-vertex-color `FillTriangle` (v1→`from`, v2/v3→`to`). `Draw` insets via `InsetConvexPolygon(pts, thickness, ...)` (full thickness, not `/2` — this is the *fill* boundary, not a stroke centerline).
- **Poly** (regular N-gon) — same ring-list approach as Circle, sampled at `sides` points instead of a full circle's segment count.
- **Polygon** (arbitrary points) — `FillPolygonGradient` generalizes the Triangle pattern to any point count (`points[0]`→`from`, rest→`to`), same fan/convexity assumption as `FillPolygon`.
- **RectangleRounded / RectangleChamfer** — share one new helper, `FillAxisGradientBoundary`, since "compute a linear-gradient color per boundary vertex and fan-fill" is identical regardless of which boundary generator produced the points. Each boundary point is **un-rotated back to the rectangle's own local frame** before computing its axis position, so the gradient rotates *with* the shape rather than staying screen-aligned — verified with a rotated (45°) rounded rectangle: per-vertex ground-truth colors confirmed the gradient axis correctly ran diagonally (rotated with the shape), not screen-horizontal. `Draw`'s fill boundary is the shape's own boundary inset by the full `thickness` via `InsetConvexPolygon` — shrinks the straight edges and the corner arcs/cuts together, concentrically, rather than reconstructing a smaller rect from scratch.

**Verification:** every new geometric piece (ring/stop-list structure, the rotation-inverse local-axis computation) rendered to a PNG and checked before trusting it, same discipline as the shape stages. All 9 stages compiled clean (0 errors, 0 warnings) throughout — final file is 2666 lines (was ~1770 before this whole redesign, ~1600 before this session's work began).

**Remaining:** the deferred partial-class file split, and a final XML-doc consistency pass. Not yet exercised inside an actual running MonoGame game — worth a manual look there before shipping, same caveat as the join/cap work above.

### Post-ship bug — Round/Bevel `Border*`/`Draw*` fill overflowing the border, found by the user running real code

The user built `DrawTriangle(v1, v2, v3, red, white, thickness: 50, join: LineJoin.Round, jointRadius: 20)` and saw the red fill overflow past the white border, with the rounded corner itself looking broken — caught by actually running the shipped code, not just re-reading it, which is exactly the failure mode this report's "verify by rendering" discipline exists to catch. Asked to check every shape for the same class of bug (`BorderTriangle`, `BorderRectangle` ×2, `BorderPoly`, `BorderPolygon`, plus every `Draw*`/`Draw*Gradient` built on top of them). This turned out to be **five separate, compounding bugs**, found and fixed in sequence — each one looked fixed after fixing the previous, until rendering the exact failing case again disproved it. Bug D was only caught because the user, unprompted, tested a second shape (`DrawRectangle`) after the first three fixes shipped and it still showed the same symptom. Bug E was only caught because the user tested with `AntialiasedEdges` on (the default) after Bug D's fix looked complete with it off — worth calling out on its own, since it's a reminder that "the shape I originally reported now renders correctly" is a narrower claim than "the bug is fixed," and that this whole investigation only ever tested the unfeathered path visually until this point (the standalone `System.Drawing` harness has no equivalent of the GPU's per-vertex alpha blending, so nothing here could have shown Bug E without the user's own screenshot).

**Bug A — `Border*`'s Round/Bevel path pre-inset the polygon before stroking it.** Every `Border*` above pre-inset the true points by `thickness/2` via `InsetConvexPolygon`, then stroked that inset polygon symmetrically — exactly correct for `LineJoin.Miter` (a linear offset that self-cancels against a symmetric stroke), but wrong for Round/Bevel, whose tangent-circle fillet construction (`ComputeJoint`) is a nonlinear function of the requested radius and doesn't self-cancel the same way. Symptom: gross overflow of the fill past the border along entire edges, worst near corners.

**Fix:** for Round/Bevel, `Border*` strokes the TRUE (un-inset) points directly, with the stroke's outer edge pinned to those points (`outerOffset=0`) and the inner edge a full `thickness` in (`innerOffset=thickness`) instead of the normal symmetric `±thickness/2` straddle — a new `inwardOnly` parameter threaded through `BuildOutlineGeometry`→`BuildRoundedOutlineGeometry`, and `ComputeJoint` generalized from a single `half` parameter to separate `outerOffset`/`innerOffset` parameters to support it (the core tangent-circle math didn't need to change, just how it's parameterized). Verified this alone eliminated the gross edge overflow — but rendering the user's exact case (thickness 50, radius 20, on a triangle with two 45° corners) still showed a real problem at those corners, disproving "fixed."

**Bug B — Fill still went all the way to the sharp vertex while the border's Round/Bevel corner receded from it.** A round join is a stroke-cosmetic detail in most vector-graphics semantics, but this project's contract ("border never exceeds the shape, always grows inward") implies something stronger for `Draw*`: fill and border must never disagree about where the shape's own boundary is. Once Bug A was fixed, the border's outer edge legitimately started cutting the corner off (a real fillet, tangent to both edges) — but `Draw*` still filled to the plain sharp vertex, leaving a real, visible sliver of fill past the rounded corner. The sliver's size wasn't cosmetic-small: a fillet's trim distance back from the vertex scales with `1/cos(halfAngle)`, so it grows sharply on an acute corner — on this triangle's 45° corners, the trim reached tens of pixels for a 20px radius.

**Fix:** a new shared helper, `BuildRoundedCornerBoundary`, rounds every corner of an arbitrary point list off by a given radius (same `ComputeJoint` tangent-circle math, `outerOffset=0`) and returns the resulting boundary — arcs (Round) or single chords (Bevel) spliced in between the original straight edges. Every `Draw*` with a Round/Bevel `join` and an active `jointRadius` now fills THIS rounded boundary (via `FillPolygon`) instead of the sharp vertices, so fill and border always describe the same rounded shape. Critically, `BuildRoundedCornerBoundary` takes the border's own `thickness` as its `ComputeJoint` clamp reference (not an unclamped sentinel) — the exact same self-intersection clamp the border's own inward-only stroke applies internally — so fill and border still agree exactly even when the requested radius has to be silently clamped down for a thick border on a tight corner (as happens on this triangle: a requested radius of 20 clamps to ~19.1 on both sides identically).

**Bug C — the straight-segment quads' inner corner wasn't properly mitered.** Surfaced by re-rendering after Bug B's fix, in the SAME acute-corner case: the straight-segment quads between joints computed each end's inner (concave-side) corner by naively offsetting that single edge along its own normal by the full `innerOffset`. For a thin stroke this is a harmless approximation (adjacent quads' inner edges overlap slightly, same solid color, no visible effect — the assumption the original code's doc comment stated). But for `Border*`'s inward-only case, `innerOffset` is the FULL stroke thickness rather than half of it, and on an acute corner (45° here) each edge's own inward normal points far enough off-axis that a 50px inward offset from one edge alone landed **past the triangle's other true edge entirely** — a genuine overflow, not a harmless overlap. Caught the same way as A/B: rendering the exact case and zooming on the acute corner showed a small but real white spike poking outside the true triangle boundary.

**Fix:** `ComputeJoint` now also computes and stores a proper mitered `InnerCorner` for the concave side — same bisector, same formula (and the same `0.2` cosine floor) `ComputeMiterOffset` already uses for a plain Miter join, just measuring `innerOffset` instead of the fillet's own radius. The two segment quads on either side of a joint now share this single point instead of each independently computing its own (necessarily different, and on a sharp corner potentially out-of-bounds) inner corner. Verified by re-deriving the failing case by hand (confirmed the naive per-edge offset landed at x=464.6 versus the triangle's true edge at x=500 — a 35px overflow) and then confirming the fix's `InnerCorner` formula reproduces exactly the point `InsetConvexPolygon` would independently compute at that same vertex.

**Bug D — the fan and the segment quads didn't actually tile the corner, leaving a real hole in the border.** After Bug C's fix, the standalone triangle render looked completely correct — flush border, fully-covered fill, verified and reported as fixed. Then the user tried a *second* shape, `DrawRectangle(x, y, 400, 50, red, white, thickness: 20, join: LineJoin.Round, jointRadius: 50)`, and saw the same class of symptom again: red fill visible through gaps at all four rounded corners. Reproducing THAT exact case standalone (rather than assuming a stale build) confirmed a real, independent bug: the join's circular fan only covers the pie-slice from `Ctr` out to the arc (between `TangentIn` and `TangentOut`), and the adjoining straight quads only reach in to `InnerCorner` — but `Ctr` and `InnerCorner` are two *different* points on the same bisector (`Ctr` sits at distance `ClampedRadius` from the vertex, `InnerCorner` further out at distance `innerOffset`), so the "kite" quadrilateral between `TangentIn`, `Ctr`, `TangentOut`, and `InnerCorner` was never covered by anything. Confirmed by rendering the fan and the quads in two different colors with nothing else drawn: a real background-colored wedge was visible at every rounded corner in both the triangle and rectangle cases.

**Fix:** two extra triangles per joint — (`TangentIn`, `InnerCorner`, `Ctr`) and (`TangentOut`, `InnerCorner`, `Ctr`) — close the kite exactly, emitted right after the fan in `BuildRoundedOutlineGeometry` (`EmitJointGapRaw`, 4 vertices/6 indices, folded into the same upfront two-pass `Reserve` the rest of the shape uses). Solid color, no feathering needed: every edge of these two triangles is interior to the border, touching the true outer boundary only at the single `TangentIn`/`TangentOut` vertices the quad and fan already feather correctly on their own. Since this lives inside the shared `BuildRoundedOutlineGeometry`, fixing it once fixed `BorderTriangle`, `BorderRectangle`, `BorderPoly`, and `BorderPolygon` together — confirmed by re-running both the triangle and the user's exact rectangle case standalone, no gap or overflow at any corner in either.

**Bug E — the antialiasing feather faded in the wrong direction whenever a closed shape's winding put `Side` at −1 (which it does uniformly for every one of its segments).** The user confirmed Bug D's fix looked correct with `AntialiasedEdges` off, but with it on (the default) still showed small artifacts ("puntos", dots) at the rounded corners — "cuando quito el AA, todo bien" (when I turn AA off, everything's fine) was the exact signal that pointed at the feathering code specifically, not the base geometry already fixed above. Root cause: `EmitTrimmedSegmentQuadRaw`'s feather band assumes its `normal` parameter points "outward" (fades to transparent along `+normal`, stays solid along `−normal`), but the actual outward direction for a given segment — established by how its endpoints were placed — is `normal * Side`, not bare `normal`; the two coincide when `Side` happens to be `+1` for a shape's winding, and are exactly reversed when it's `−1`. A closed polygon has the *same* `Side` at every one of its joints (consistent winding), so this wasn't a one-off — every segment of every closed Round/Bevel border had its feather fading backwards whenever the shape happened to be wound the `Side = −1` way (confirmed: this triangle and rectangle both are). The visible effect: the border's solid color extended slightly *past* the true outer edge with a hard, un-antialiased boundary against the background, while ~1px *inside* the true edge it faded to transparent, letting the fill peek through in a thin band — most visible where it interacted with the (correctly-feathered) fan/gap geometry at each rounded corner, which is why it looked like small dots there rather than a uniform issue along the straight edges.

**Fix:** pass `normal * sideA` into `EmitTrimmedSegmentQuadRaw` instead of bare `normal` (`sideA` was already computed per-segment for positioning `outerA`/`innerA`, just never applied to the feather direction). Verified two ways: (1) numerically — re-derived the quad's inset feather-boundary point by hand for the triangle's `v1` joint and confirmed it now lands exactly (`diff = 0`) on the same point `EmitJoinFanRaw`/`EmitJointGapRaw`'s independent radial computation produces, where before the fix the two disagreed by a full `FeatherWidth` (1.0px) in a direction matching the segment's own normal — the fingerprint of exactly this sign bug; (2) generalized — ran the same numeric check across every joint of a regular pentagon in **both** winding directions (CCW and reversed/CW) plus an irregular 5-point polygon with mixed acute/obtuse corners, all passing, confirming the fix isn't triangle/rectangle-specific and correctly handles whichever `Side` a given winding produces rather than hard-coding an assumption.

**Shapes NOT affected, checked explicitly:** `BorderRectangleRounded`/`BorderRectangleChamfer` are Miter-only internally (no `join` parameter exposed at all — the redesign deliberately kept the cheaper pre-sampled-arc-plus-Miter approach there, never the tangent-fillet machinery), so this whole bug class doesn't apply. `BorderCircle`/`BorderEllipse` build their ring directly via `DrawRing`, never touching the outline engine's join logic. `DrawPolyGradient`/`DrawCircleGradient`/`DrawEllipseGradient`/`DrawRectangleRoundedGradient`/`DrawRectangleChamferGradient` don't expose `join`/`jointRadius` at all. `DrawTriangleGradient`/`DrawPolygonGradient` DO expose them and call the now-fixed `Border*` — their own gradient-fill inset (needed so the gradient stops near where the border begins) is capped at `min(thickness, jointRadius)` rather than the full `thickness`, since insetting an arc by more than its own radius crosses through the arc's center and inverts it; since the border is drawn on top right after, any resulting sub-thickness gap is simply covered, not a visible seam — a pragmatic, deliberately-imprecise fix accepted because the fill is never the top-visible layer there, unlike Bugs A–E above where the wrong geometry WAS directly visible. Bug E (the feather sign) also transitively affects `EmitRoundCap`/`EmitLineSegment` usage sites (any Round-capped open line) only through `EmitJoinFanRaw`'s already-fixed core/outer convention — `EmitLineSegment` itself was already correct (it's what Bug E's fix was modeled after) and open polylines don't have the closed-shape uniform-`Side` issue in the first place.

**Verification method:** every fix in this sequence was checked by reproducing the exact vertex/joint math standalone (`System.Numerics.Vector2`, no MonoGame dependency) and rasterizing the actual triangle list to a PNG via `System.Drawing`, then visually inspecting both the wide view and a zoomed crop of each corner — the same discipline that caught the original join-radius bug, and the only reason Bugs B through E were caught at all, since each one looked plausible (and in Bug D's case, looked *fixed*) from reading the previous fix alone. Bug E specifically could only be confirmed numerically (matching feather-boundary coordinates), not visually through this harness, since `System.Drawing` has no equivalent of the GPU's per-vertex alpha interpolation — the geometric *position* of the mismatch was verifiable standalone, but its visual *appearance* as "dots" needed the user's own screenshot to confirm the hypothesis was worth pursuing at all. Final renders of the user's original triangle case (thickness 50, `jointRadius` 20, 45°/45°/90°) and the follow-up rectangle case (thickness 20, `jointRadius` 50, a "pill" shape) show the border flush with the true edges at every corner and the fill fully contained within it, with no overflow and no gap anywhere; the feather-boundary numeric check passes on both, plus a pentagon in both windings and an irregular polygon.

**Unresolved, superseded by the section below:** after Bug E's fix shipped, the user found a *further* symptom on a third shape/parameter combination — two small, fully-opaque, isolated red squares floating well inside the white border area, nowhere near any edge or joint. This doesn't match the profile of any of Bugs A–E (all of those are edge/seam effects — a fade, a gap, an overflow — never an isolated interior block of the wrong color), so it was still open, not yet root-caused, when the decision below made it moot: geometric feathering was removed from the engine entirely, so there is no more feather code left for that symptom to live in. If an isolated-block artifact like it resurfaces post-removal, it was never a feathering bug and needs its own investigation (candidates going in: a degenerate/misordered vertex in `FillPolygon`'s first-vertex fan triangulation, or stale data from buffer reuse — see **C1**).

### Geometric antialiasing (feathering) removed — MSAA handles it now

**Decision, from the user:** after testing MSAA (4x, set via `GraphicsDeviceManager.PreferMultiSampling`/`PreparingDeviceSettings`) and finding it visually comparable to this engine's geometric feathering at better performance, the user asked to drop feathering from the library entirely and rely on MSAA instead — "only thw draw part will remaing[sic], the AA will be handle by the MSAA." This also makes the entire Bug E investigation above moot going forward (there is no more feather-direction sign to get wrong), though it's kept in this report as the historical record of a real bug that existed while feathering was still in the codebase.

**What was removed:** the `AntialiasedEdges` property, the `antialiasedEdges` parameter on both `Begin()` overloads, `WithAlpha` (used only to build feather-transparent colors, now dead), and the `FeatherWidth` constant. Every `bool feather`/`bool? feather` parameter threaded through the outline engine was removed, and each function collapsed to its single (formerly "unfeathered") code path: `EmitLineSegment`, `EmitTrimmedSegmentQuadRaw`, `EmitJoinFanRaw`, `EmitRoundCap`, `JoinFanCounts`, `BuildMiterOutlineGeometry`, `BuildRoundedOutlineGeometry`, `BuildOutlineGeometry`. `EmitJointGapRaw` (the Bug D kite-closer) lost its `radius`/`feather` parameters along with the core-radius inset math that only existed to stay in agreement with the feathered fan — it just uses the plain tangent points now. `FillEllipse`/`DrawEllipse`/`BorderEllipse`/`DrawRing` each lost their separate feather-skirt pass and reverted to a single solid-fill pass. Net: 313 lines removed (3018 → 2705), zero new warnings.

**Corner segment density bumped slightly, at the same time, per the user's request** ("make the corner using more segments, just a little more"): `SegmentsForArc`'s per-radius coefficient went from `1.8` to `2.2` (~22% more segments at a given radius) and `MinCircleSegments` from 6 to 8. Rationale: MSAA smooths triangle *edges*, but a rounded corner's smoothness is a *tessellation* concern (how many flat facets approximate the true arc) — MSAA doesn't touch that at all, and geometric feathering's soft fade had been incidentally softening facet-edge visibility too, a side effect that's now gone along with it. A small density bump keeps curves reading as smooth without over-spending triangles (`MaxCircleSegments` cap unchanged at 128, so this only affects small-to-medium arcs, not already-maxed-out large circles).

**Verification:** full file compiles clean (0 errors, 0 warnings) after the removal. Not yet re-verified visually against MSAA in an actual running game — this removal is large enough (every curved/joined shape's rendering path changed) that it's worth the user's own visual pass before shipping, same caveat as every other unexercised-in-a-real-game item in this report.

## REQUESTED FEATURES — Gradient fills (not yet implemented) — superseded by the v2 redesign above; naming below is stale (`DrawCircleGradient` etc., not `Fill*`/`Draw*Gradient`), kept for the original spec's reasoning

**Context:** the library already has partial gradient support. This is a request to round it out to three shapes, plus a new offset control for the existing circle gradient. Nothing in this section has been implemented yet — listed here as a spec to confirm before coding.

### [F1] Rectangle gradient — vertical and horizontal
**Current state:** already covered. `DrawRectangleGradient(Rectangle rect, Color from, Color to, bool horizontal)` (line 713) already fades `from → to` across the rectangle, and the `horizontal` flag already switches between a left→right and a top→bottom fade.
**How it applies:** no new code needed — call the existing method with `horizontal: true` for a horizontal fade, `horizontal: false` for a vertical one. Nothing to add here unless a different call shape (e.g. two dedicated `DrawRectangleGradientH`/`DrawRectangleGradientV` methods instead of a bool flag) is specifically wanted.

### [F2] Triangle gradient — first vertex to the other two
**Current state:** partially covered. `DrawTriangle(Vector2 v1, Color c1, Vector2 v2, Color c2, Vector2 v3, Color c3)` (line 598) already interpolates color per-vertex across the triangle (barycentric — this is just how GPU vertex-color rasterization works, no extra code required).
**How it applies:** the specific case requested — `v1`'s color fading out to a single second color at `v2` and `v3` — is just this existing method called as `DrawTriangle(v1, fromColor, v2, toColor, v3, toColor)`. A thin convenience overload can be added if a two-color call is preferred over repeating `toColor` twice:
```csharp
public void DrawTriangleGradient(Vector2 v1, Vector2 v2, Vector2 v3, Color from, Color to)
    => DrawTriangle(v1, from, v2, to, v3, to);
```
Simple, no new geometry/batching logic — it's a one-line wrapper around what already exists.

### [F3] Circle gradient with inner/outer offset — new
**Current state:** `DrawCircle(Vector2 center, float radius, Color inner, Color outer)` (line 823) already fades `inner → outer` across the full radius (center to edge), with no way to hold either color solid before the fade starts.
**Requested addition:** a new method — `DrawCircleGradient` or similar — with two extra parameters, `innerOffset` and `outerOffset`:
- `innerOffset`: the fade doesn't start at the center. From radius `0` to `innerOffset`, the circle is solid `inner` color. The gradient only begins at distance `innerOffset` from the center.
- `outerOffset`: the fade doesn't reach the edge. From `radius - outerOffset` to `radius`, the circle is solid `outer` color. The gradient ends at distance `radius - outerOffset`.
- Both can be used together — the gradient then runs only in the band between `innerOffset` and `radius - outerOffset`.
- **Validation needed:** `innerOffset + outerOffset` must not exceed `radius`, or the two bands overlap and the gradient band inverts/collapses. Needs a decision on behavior when violated — clamp (same precedent as **M2**'s thickness-vs-radius clamp) vs. throw `ArgumentOutOfRangeException` (matching **L6**'s general robustness-hardening theme). Flagging for confirmation rather than picking unilaterally, per the project's "no design decisions without confirmation" convention already used elsewhere in this report (see **L5**).

**Proposed signature (draft, for confirmation):**
```csharp
public void DrawCircleGradient(Vector2 center, float radius, Color inner, Color outer,
    float innerOffset = 0f, float outerOffset = 0f)
```
**How it applies:** most likely implemented as its own function (as noted in the request) rather than folded into the existing `DrawCircle(center, radius, inner, outer)` overload, since it needs a different per-vertex color ramp (3 color zones — solid/gradient/solid — instead of 1 continuous fade) and would only pay that extra cost when offsets are actually used. Default `innerOffset = 0f, outerOffset = 0f` reproduces today's `DrawCircle(center, radius, inner, outer)` behavior exactly, so existing call sites are unaffected.

## LOW

### [L1] Unused local variable `innerFeatherDist` — `[Duplication/Dead code]`
**File/Line:** `DrawEllipseLines` (computed, never read — the code recomputes the same value inline instead). Note: `vi` (old `BuildPolygonOutlineGeometry`) and `n_next` (old `BuildPolylineOutlineGeometry`) no longer exist after the **M3** unification, so this item shrank to one variable.
**Impact:** Minor reader confusion; would trigger an unused-variable compiler warning if warnings were enabled.
**Proposed fix:** Remove the variable.

### [L2] `Math.Sqrt`/`Math.Cos`/`Math.Sin` (double) used instead of `MathF` equivalents in per-call paths — `[Performance]`
**File/Line:** `SegmentsForArc` (`Math.Sqrt`); `DrawRectangle(Rectangle, Vector2, float, Color)` (`Math.Cos`/`Math.Sin`).
**Impact:** Small, avoidable double↔float conversions in code the class's own design philosophy says should avoid this kind of per-call overhead.
**Proposed fix:** Use `MathF.Sqrt`/`MathF.Cos`/`MathF.Sin` throughout.

### [L3] A few compound methods still no-op on degenerate input before any `EnsureStarted()` check runs — `[Bug/API]`
**File/Line:** `DrawLineDashed`, `DrawRectangleLines`, `DrawPolyLines`, `DrawSplineLinear` (early-return on zero-length/degenerate input). Note: this is now fixed for `DrawPixelFast`, `DrawLineStrip`, `DrawSplineCatmullRom`, and `DrawSplineBezierCubic` as a side effect of H1/H2/H5.
**Explanation:** These remaining methods return early on degenerate parameters before reaching any inner call that would validate `Begin()` was called.
**Impact:** Low severity (only manifests with already-degenerate input), but could mask a genuinely forgotten `Begin()` call during development.
**Proposed fix:** Move the `EnsureStarted()` check before the early-return checks, for consistency.

### [L4] `DrawEllipse`'s antialiased fill re-generates rim vertices already produced by the fan pass — `[Performance]`
**File/Line:** `DrawEllipse` fan loop; `EmitEllipseFeather`.
**Explanation:** Both loops sample the unit circle at the same angles and push near-duplicate rim vertices — a deliberate simplicity/robustness trade-off (each reserved chunk stays self-contained even if a flush happens in between).
**Impact:** Minor CPU overhead per antialiased circle/ellipse draw; not worth fixing unless it shows up in profiling.
**Proposed fix:** Leave as-is, but add a one-line comment explaining the trade-off explicitly.
**Superseded:** the feather pass this entry refers to was removed entirely — see "Geometric antialiasing (feathering) removed" below. `DrawEllipse`/`FillEllipse` are single-pass now, so this finding no longer applies.

### [L5] `MaxCircleSegments` is public while its sibling tunables are private — `[API]`
**File/Line:** constants block at the top of the class.
**Impact:** Minor inconsistency; a consumer choosing an explicit `segments` count can see the max but not the min.
**Proposed fix:** Either make `MinCircleSegments` public too, or make `MaxCircleSegments` private/internal — needs a product decision, flagged for confirmation per project rules on public API changes.

### [L6] No upper-bound validation on `initialVertexCapacity`, `sides`, `segments`, or `points.Length` — `[Robustness]`
**File/Line:** constructor; `DrawPoly`/`DrawPolyLines`; `DrawCircleSector`/`DrawRing`; `DrawTriangleFan`/`DrawTriangleStrip`/`DrawPolygonOutline`.
**Explanation:** None of these public entry points validate their counts. Very large values can overflow `int` math inside `Reserve(...)`-style calls or simply exceed fixed buffer capacity, surfacing as an unhandled `IndexOutOfRangeException` instead of a clear validation error.
**Impact:** Low in a typical trusted-game-code context, but worth hardening if this library ever renders externally-sourced geometry.
**Proposed fix:** Add explicit range checks (`ArgumentOutOfRangeException`) at the public API boundary for these parameters.

### [L7] Monolithic single-file/class design — `[Structure]`
**File/Line:** whole file, single `sealed class PrimitiveBatch`.
**Impact:** Purely organizational; navigability and code-review focus suffer at this size.
**Proposed fix:** Split into `partial class PrimitiveBatch` across multiple files (Core, Lines, Shapes, Splines) — zero public API impact, pure file reorganization.

### [L8] No usage-example snippet in the class-level doc comment — `[Docs]`
**File/Line:** class-level doc comment.
**Impact:** Minor onboarding friction for new consumers of the library.
**Proposed fix:** Add a short `<example>`/`<code>` block showing the typical `Begin(); Draw...(); End();` pattern.
