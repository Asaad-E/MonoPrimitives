# Roadmap

Known gaps and queued ideas. Check before proposing something "obviously missing" — it may be a deliberate deferral, not an oversight.

## Deferred on purpose (don't build without asking)

- **Named input-action mapping** (register `"Jump"` once, rebindable). `PrimitiveInput` deliberately stays low-level (`IsKeyDown`/`GetAxis`/`GetVector2` + raw device queries) — a full action-map layer is real infrastructure beyond what's been asked for.
- **Shader-based screen-space antialiasing.** Built twice (search-based FXAA, then a simpler edge-aware blend), both verified rendering correctly, both shelved anyway — see DECISIONS.md. Don't rebuild this without a concrete reason MSAA isn't enough. **Circle-specific edge feathering was evaluated separately (non-shader, a vertex-alpha gradient ring) and hits the same wall — see DECISIONS.md.**

## Known bugs, documented but not fixed

- **`InsetConvexPolygon` picks the wrong inward direction at some reflex vertices** — affects every `Border*`/`Draw*Gradient` on a concave polygon that goes through it (confirmed on `DrawPolygonGradient`; `BorderPolygon`'s own doc comment already flagged the general risk, but not this precisely). Root cause: at each vertex it computes two candidate offset points (`curr ± miterOffset`) and picks whichever is closer to the polygon's centroid — a heuristic that only works because a convex vertex's inward direction always points toward the centroid. At a REFLEX vertex that assumption can simply be false, and when the centroid happens to coincide with (or sit very close to) the reflex vertex itself, the two candidates become an exact (or near-exact) tie, which resolves via the code's `<` comparison to a specific side regardless of which one is actually correct.
  - **Confirmed repro**: the gallery's `LShape` (6 points, reflex vertex at `(0,0)`, whose centroid is *exactly* `(0,0)` too — a fully symmetric L). Hand-replicating the exact formula gives both candidates `distSq = 32.00` at that vertex — an exact tie — and the chosen point `(4,4)` lands in the shape's empty notch, not its solid material. Every other vertex resolves correctly (e.g. `(-70,-70) -> (-66,-66)`, clearly inward). Visible as a distorted diagonal cutting through `DrawPolygonGradient`'s fill at the wrong angle; not obviously visible on a flat-colored `BorderPolygon` stroke, which is likely why this went unnoticed until a gradient made the shape distortion visible.
  - **What a real fix needs to account for**: don't infer "inward" from distance-to-centroid at all — determine each vertex's convex/reflex status directly from its own turn direction (the same cross-product sign `IsConvex` already computes per-vertex, just needs exposing per-vertex instead of only as a whole-polygon convex/not-convex bool), and pick the offset side using that, not a centroid comparison. Needs verifying against every existing call site that depends on `InsetConvexPolygon` (~15: `BorderPolygon`, `BorderTriangle`, `BorderRectangle`, `DrawPolygonGradient`, the drop-shadow methods, etc.) since some of those may be relying on the current (buggy-for-reflex) behavior for polygons that happen to work out fine today. Don't touch without re-verifying all of them by rendering, not just reasoning.

- **`DrawLineStrip3D`/`Trail3D.Draw` show a visible gap/overlap at a bend when `thickness` isn't tiny relative to segment length.** Both draw each segment as its own independent camera-facing quad (`DrawLine3D` in a loop) — each segment computes its own `side = normalize(cross(dir, toCamera))`, and two segments meeting at an angle generally compute *different* `side` vectors at their shared point, so the "same" corner lands in two different places. Confirmed numerically (not just reasoned): a moderate bend at `thickness=1.5` produced a 0.41-unit gap between the two segments' versions of the shared corner — about 27% of the thickness itself, clearly visible at typical debug-line widths. 2D's own spline system solved the equivalent problem with `BuildOutlineGeometry` (a proper shared-vertex strip with miter/bevel/round joins) — 3D has no analogous joined-billboard-strip builder; fixing this properly means designing one (choosing a consistent per-vertex offset direction across two differently-facing segments, still camera-facing), not a small patch. Not attempted this pass — a real, deliberate deferral, not an oversight.

## Real gaps, not yet built

- **NuGet: published.** `MonoPrimitives 0.3.0` is live on nuget.org (`dotnet add package MonoPrimitives`), via `.github/workflows/publish.yml` (GitHub Release → NuGet Trusted Publishing, OIDC, no stored API key).
- **CI is publish-only** (`publish.yml`, triggered by GitHub Release) — no build/test-on-PR workflow yet.
- **FNA/KNI: not supported, source-portable in principle only.** Evaluated on request, not built: the library only touches "core XNA4" surface (`BasicEffect`, `GraphicsDevice.DrawUser*Primitives`, `Texture2D.SetData`, standard math/input types) — no custom shaders (the #1 usual FNA/MonoGame incompatibility), no content pipeline, no P/Invoke, which is the best-case profile for portability. Two concrete blockers found anyway: (1) `PrimitiveType.PointList` (`Primitives2D.cs`'s `DrawPixelFast`/`FlushPoint`) is stock MonoGame's name for the primitive FNA calls `PointListEXT` — a one-line fix if ever needed; (2) KNI uses an entirely different root namespace (`nkast.Xna.Framework`, not `Microsoft.Xna.Framework`) — every `using` in every file would need rewriting, not a one-liner. Neither matters practically without a separate build target regardless: a prebuilt `MonoPrimitives.dll` referencing `MonoGame.Framework.DesktopGL` can't be passed an FNA/KNI project's own `Vector2`/`Color` values — same names, different CLR types, no binary compatibility across XNA-alike implementations exists. Real support would mean a second build (swapped `PackageReference`, separate `TargetFramework` or sibling project), not a shared DLL — don't build this speculatively.
