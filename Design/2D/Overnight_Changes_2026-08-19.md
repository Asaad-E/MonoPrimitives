**Bug/edge-case audit (item 1), complete — 3 real bugs found and fixed:**

1. **Crash (`ArgumentException`) on negative-dimension `Rectangle` in the Rounded/Chamfer families.** `GenerateRoundedRectBoundary`/`GenerateChamferRectBoundary` computed `maxR`/`maxC = MathF.Min(rect.Width, rect.Height) * 0.5f` then fed it to `Math.Clamp(radius, 0f, maxR)` — `Rectangle` allows negative `Width`/`Height` (MonoGame doesn't validate it), and a negative `maxR` makes `Math.Clamp`'s own min>max check throw. Reachable from all 10 Rounded/Chamfer methods. Fixed with `MathF.Abs` on both dimensions before the `Min`; plain `FillRectangle`/`BorderRectangle` already tolerated negative dimensions fine (just inverted geometry, no crash), so this brings the families in line with each other.
2. **`origin` was absolute in 4 places, relative everywhere else — silently broke `DrawRectangleGradient`'s "fill and border rotate together" claim.** `FillRectangle`/`BorderRectangle`/`DrawRectangle` all correctly treat an explicit `origin` as an offset from the shape's own `(x,y)` (`pivot = origin ?? center; ox = x + pivot.X`). Four sibling spots used `origin` as a raw absolute world coordinate instead whenever it was non-null: `FillRectangleGradient`, the shared `FillAxisGradientBoundary` helper (used by RectangleRounded/Chamfer gradients), `GenerateRoundedRectBoundary`, and `GenerateChamferRectBoundary`. Practical effect: any call with an explicit `origin` and non-zero `rotation` rotated its fill about a completely different point than its border — invisible when `origin` is left `null` (both default to the same center), which is presumably why it went unnoticed. Fixed all 4 to the same relative convention; `DrawRectangleGradient` additionally needed its inset fill's `origin` shifted by `-thickness` so the fill (drawn from a shrunk `x+t,y+t`) and the border (drawn from the true `x,y`) land on the exact same absolute pivot. Verified by standalone render — before: fill and border visibly rotate apart; after: they move as one rigid shape (`origin_pivot_buggy.png` / `origin_pivot_fixed.png`).
3. **Uncatchable `StackOverflowException` risk — several `stackalloc` buffers sized directly off caller-controlled counts, no upper bound.** Unlike `SegmentsForArc` (always internally capped at `MaxCircleSegments`), these took the caller's number as-is: `BorderPoly`/`DrawPoly`'s rounded-corner branch (`sides`, only checked `< 3`), `BorderPolygon`/`DrawPolygon`/`DrawPolygonGradient`'s rounded-corner branches (`points.Length`, an arbitrary caller span — the `× (MaxCircleSegments+1)` multiplier form is the worst offender, a few hundred points with `jointRadius` set already overflows a 1MB stack), `BuildRoundedOutlineGeometry` (reachable via `DrawLineStrip` with Round/Bevel join on a long span), and both spline methods (`segmentsPerPiece` has no upper bound). Fixed with a small stack/heap threshold switch at each site — `Span<Vector2> buf = n <= MaxStackAllocElements ? stackalloc Vector2[n] : new Vector2[n];` (new `MaxStackAllocElements = 4096` / `MaxStackAllocJoints = 512` constants, ~30KB budget either way) — degrades a pathological input to one small GC allocation instead of crashing the process; zero behavior change for every realistic call, which still takes the stackalloc branch exactly as before. The multiplier-form sites compare `sides`/`points.Length` against the divisor rather than the product, so the stackalloc branch's own size expression can't int-overflow. Triangle's and the plain Rectangle-family's `stackalloc [fixedCount × (MaxCircleSegments+1)]` sites were NOT touched — their multiplier is a hardcoded 3/4/8, not caller-controlled, so they were never at risk.

Everything else the audit checked came back clean: `SafeNormalize`/`ComputeJoint`'s divisions all guard zero-length/near-180°/near-zero-bisector cases already; Triangle's rotation only mutates its own by-value local copies, never caller state; every other `stackalloc` is sized off a fixed small count or `SegmentsForArc`'s own capped output; gradient `innerOffset`/`outerOffset` overlap handling is the same "scale down proportionally" rule everywhere.

All fixes recompiled clean in both scratch projects (with and without `Nullable enable`).

**Found a real usage trap in `SmoothZoom` (both `Camera2D` and the 3D `Camera3D`), fixed via documentation, not a code change.** Calling `SmoothZoom(delta, dt)` every frame with a small nonzero `delta` — the natural way to write "hold + to zoom in continuously" — doesn't climb smoothly the way you'd expect: each call adds `delta` onto the *in-flight target*, not onto the current eased `Zoom`, so a delta repeated every frame races the target toward the clamp almost immediately instead of tracking a gradual per-frame increase. Confirmed by literally reproducing that exact call pattern (300 frames of `SmoothZoom(1f, dt)`) and watching the zoom shoot straight to `MaxZoom` instead of settling near the expected `1 + 1 = 2`. The design is *correct* for its intended use — discrete input like mouse wheel ticks, where `delta` is naturally 0 on all but a handful of frames, which is exactly how `Camera3D`'s own `Update` already calls it — so the fix was clarifying both doc comments with the distinction and pointing continuous-input callers at adjusting `Zoom`/distance directly by `rate * deltaSeconds` instead. Recompiled clean.

## `SpatialHashGrid2D.cs` (new) — fast neighbor queries for simulation prototyping

Looked into how boid/flocking and crowd simulations actually handle "who's nearby" at scale, since a naive check-every-pair-of-agents approach becomes the bottleneck fast — the standard answer is a uniform spatial hash grid: bucket entities by which grid cell they're in, then a radius query only checks the handful of cells the query circle can touch instead of every entity. Added `SpatialHashGrid2D<T>`: `Clear()`/`Insert(item, position)` once per entity per frame, then `QueryRadius(center, radius, results)`. Generic over any item type (an id, a reference — whatever identifies your entity). Directly serves flocking, predator-prey, and pandemic-contact scenarios, where "find everyone within radius R" is the operation that actually matters for performance. Verified against a brute-force all-pairs scan over 500 random points across 20 random queries — exact match every time (not just "close," since a hash-grid bug would usually show up as *missing* neighbors near a cell boundary, which a brute-force diff catches precisely).

## Real bug found while reviewing that claim: `BlendState.AlphaBlend` default was wrong for every translucent color in both libraries

Went back to actually check the claim above instead of trusting it, and it doesn't hold up. `BlendState.AlphaBlend` in XNA/MonoGame is the **premultiplied**-alpha preset (`ColorSourceBlend = One`) — it expects the source color's RGB to already be scaled by its own alpha before reaching the GPU. Neither library does that: `PrimitiveBatch.PushVertex` (2D) and `Primitive3DBatch.PushTriangleUnchecked`/`PushLine` (3D) both write the `Color` straight through, unmodified. Every `new Color(r, g, b, a)` anywhere in either library — including `GridColor`/`AxisLineColor` in `Plot2D`, the `FilledLine` fill alpha, and the just-added low-alpha 3D grid defaults (see below) — is a straight (non-premultiplied) color. Fed to a premultiplied blend state, a translucent draw renders far more opaque than its alpha value implies.

Worked the actual blend equation by hand to confirm before touching anything: a grid line at alpha 0.15 over a dark background should blend to ≈0.181, but under `AlphaBlend` fed a straight color it actually blends to ≈0.818 — essentially a bright, nearly-opaque line instead of a faint one. `Plot2D`'s filled-area alpha (0.35) comes out ≈0.152 instead of the intended ≈0.087, about 1.75× too strong. A **fully opaque** fill (alpha=255, the overwhelming majority of every existing draw call) is unaffected either way — `AlphaBlend` and `NonPremultiplied` produce byte-identical results once alpha=1, so this was a silent bug specifically in the (currently small but growing, and just-requested) translucency features, not something that would show up in the ordinary solid-shape usage this library has mostly had so far.

**Fix:** both `PrimitiveBatch.Begin` (2D) and `Primitive3DBatch.Begin` (3D) now default to `BlendState.NonPremultiplied` instead of `BlendState.AlphaBlend` — the blend state that actually matches every color this codebase constructs (straight RGBA, no premultiply step anywhere). Zero call sites needed to change; this is purely a default-blend-state fix. `dotnet build` on the real project still succeeds. Not independently re-verified against a live `GraphicsDevice` (none available in this environment, same limitation as everything else this session) — the fix follows directly from XNA/MonoGame's own documented `BlendState.AlphaBlend`/`BlendState.NonPremultiplied` semantics, which is why the blend-equation arithmetic above was worked out explicitly rather than asserted.

## `DebugFont5x7.MeasureText` — trailing glyph-gap only stripped from the string's last line, not from every line

A subagent reviewing `DebugFont5x7.cs` (the other file that had had the least scrutiny, alongside `Primitive3DBatchShapes.cs` — see the 3D log for that half of its findings) caught this; verified it by hand-tracing before fixing. The "no trailing gap after the last glyph" correction (`if (lineWidth > 0f && lastChar != '\0') lineWidth -= glyphSpacing * pixelSize;`) sat *after* the `foreach` loop over the whole string, so it only ever ran once — for whichever line happened to be last. Every earlier line's width got folded into `maxWidth` at its own `\n` *before* that correction existed for it, so any multi-line string where the widest line isn't the last one had `MeasureText` overstate the width by `glyphSpacing * pixelSize`.

Hand-traced `"HELLO\nHI\nWORLD"` at `pixelSize=2, glyphSpacing=1`: true per-line widths are 58/22/58 (max 58), but the old code returned `maxWidth=60` — "HELLO" (the actual widest line, tied with "WORLD") got captured 2px too wide at its `\n` since only the string's literal last line ever received the correction. Fixed by applying the same correction at *each* `\n` (right before that line's `maxWidth = Max(...)` comparison), not just once after the loop — the existing height calculation right next to it was already correctly per-line (never adds a trailing `lineSpacing` past the last line), confirming that was the intended behavior, just applied in the wrong place for width. Since `MeasureText`'s own doc comment says this exists "for centering/layout before drawing," this was silently mis-centering any multi-line debug text where an earlier line was the widest one. `dotnet build` succeeds.

## Rounded corners for `Triangle`/`Polygon` Fill (and a real pre-existing bug this exposed)

Requested: the same "curved corners" `RectangleRounded` already has, but for `Triangle` and arbitrary `Polygon`, without slowing down the existing sharp-shape paths. Turned out the actual corner-fillet math already existed internally (`ComputeJoint`/`BuildRoundedCornerBoundary`, used today by `Draw*`'s `LineJoin.Round`/`Bevel` options) — so this was mostly about exposing it as its own entry point, not writing new geometry from scratch.

New: `FillTriangleRounded`/`BorderTriangleRounded`/`DrawTriangleRounded` (2 overloads) and the same four for `Polygon`. `Fill*Rounded` is a genuine standalone Fill — no border pass at all, cheaper than the "call `Draw*` with a matching fill/border color" workaround, and correct in cases that workaround isn't (see below). The existing sharp `FillTriangle`/`FillPolygon`/etc. are completely untouched — every new method is additive, so ordinary usage pays nothing for this.

**Real bug found and fixed while verifying this (not something I introduced — a pre-existing gap in `ComputeJoint`, just never triggered before):** `ComputeJoint`'s corner-radius clamp caps each corner's own trim distance at ≤90% of its own view of an adjacent edge — correct in isolation, but that's a *per-corner* budget, not a *per-edge* one. Two corners sharing the same edge can each independently claim up to 90% of it, together wanting up to 180% — their tangent points cross past each other and the fillet self-intersects. Rendered a concrete case to check (a ~60°-angled, ~70px-edged triangle, 25px corner radius) and got exactly that: visible spikes at every corner (`rounded_corner_fill_test.png`, before/after). This never showed up on `Draw*`'s existing `Round`-joined corners because those couple the radius to a border `thickness` that's normally small next to the shape — `ComputeJoint`'s *other* clamp (against that thickness) was already the binding one, so the per-edge conflict never had room to occur. The new `Fill*Rounded` methods are the first case with no border thickness to lean on and often a deliberately generous radius, which is exactly the regime where it does.

Fixed with a new `ClampCornerRadiusToFit` — computes, per edge, the largest radius the two corners sharing it could together support without crossing (via the plain isoceles fillet formula, `tangentDistance = radius / tan(halfAngle)`, per vertex), and takes the minimum across the whole shape. Applied before calling into the existing `ComputeJoint`/`BuildRoundedCornerBoundary` machinery, which is otherwise untouched — deliberately scoped to just the new `*Rounded` methods rather than changing `ComputeJoint`'s own long-used 90% constant globally, since that's shared by many already-verified call sites (`RectangleRounded`, `RectangleChamfer`, every existing `Round`/`Bevel`-joined `Draw*`) and a global change would need re-verifying all of them, not just this new feature. Re-rendered the same failing triangle after the fix: clean, no self-intersection (`rounded_corner_zoom.png`). `dotnet build` succeeds.
